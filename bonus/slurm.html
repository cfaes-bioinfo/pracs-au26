1 Introduction

This page covers some additional Slurm topics that build on the w10a and w10b lectures: more sbatch options, Slurm environment variables, copying Slurm log files to output dirs, interactive shell jobs, customizing squeue output, checking how many resources your jobs used, and ways to automate multi-step workflows with Bash and Slurm.

To run the commands on this page yourself, start a VS Code session at https://ondemand.osc.edu in /fs/ess/PAS3493/people/$USER, as per usual.

2 More sbatch options

2.1 Requesting large amounts of memory

The maximum amount of memory you can request on regular Pitzer compute nodes is 178 GB. If you need more than that, there are specialized largemem or hugemem nodes.

Switching to such a node generally happens automatically based on your requested amount. Unfortunately, there are “gaps” between the maximum and minimum amounts of RAM on these node types, which means that certain amounts of memory cannot be requested on any node (see this OSC page for details on Pitzer nodes).

To make sure that a batch job runs on one of these node types, you can also request it explicitly with the --partition option. For example:

myscript.sh (excerpt)
#!/bin/bash
#SBATCH --partition=hugemem
#SBATCH --mem=900G

2.2 Separating standard output and standard error

By default, both stdout and stderr end up in the same Slurm log file, but you can separate them into different files with the --error option, e.g.:

myscript.sh (excerpt)
#SBATCH --output=slurm-fastqc-%j.out
#SBATCH --error=slurm-fastqc-%j.err

In the above example, only stdout will go into the file specified with --output, and stderr will go into the file specified with --error. Separating stdout and stderr like that could be useful because it may make it easier to spot errors, and an empty --error file would mean that there were no errors.

However, reality is more messy: some programs print their main output (results) not to a file but to standard out, in which case all logging output, i.e. errors and regular messages alike, is designated as standard error. And some other programs use stdout for all messages. Therefore, with Slurm, I personally only specify --output, such that both stdout and stderr end up in that file.

2.3 Get warned when your job is close to its time limit

You may also find the --mail-type values TIME_LIMIT_90, TIME_LIMIT_80, and TIME_LIMIT_50 useful for very long-running jobs, which will warn you when the job is at 90/80/50% of the time limit. This can be useful because you can email OSC to ask for an extension on individual jobs. You shouldn’t do this often, but if you have a job that ran for 6 days and it looks like it may time out, this may well be worth it.

myscript.sh (excerpt)
#SBATCH --mail-type=TIME_LIMIT_90,FAIL

3 Slurm environment variables

Slurm automatically makes a number of environment variables available inside a shell script that you submit as a batch job, such as:

Variable Corresponding option Description
$SLURM_JOB_ID — Job ID assigned by Slurm
$SLURM_JOB_NAME --job-name Job name (by default, the name of the script)
$SLURM_CPUS_PER_TASK --cpus-per-task Number of reserved cores
(only set if you used --cpus-per-task)
$SLURM_MEM_PER_NODE --mem Amount of reserved memory in MB
(only set if you used --mem)
$SLURM_SUBMIT_DIR — Path to the dir from which the job was submitted
$TMPDIR — Path to fast temporary storage on the compute node
(set by OSC, not Slurm)

As an example of how these environment variables can be useful, compare these two ways of telling the program STAR how many threads to use. First, hardcoding the number of threads, which means the number has to be specified twice:

star.sh (excerpt)
#SBATCH --cpus-per-task=8

STAR --runThreadN 8 --genomeDir [...]

Second, using $SLURM_CPUS_PER_TASK, so that the number is only specified once, in the Slurm option:

star.sh (excerpt)
#SBATCH --cpus-per-task=8

STAR --runThreadN "$SLURM_CPUS_PER_TASK" --genomeDir [...]

With the second strategy, you will automatically use the correct (requested) number of cores, and don’t risk having a mismatch. Also, if you need to change the number of cores, you’ll only have to modify it in one place.

WarningThese variables don’t always exist

As noted in the table, some of these variables are only set if you used the corresponding option: for example, $SLURM_CPUS_PER_TASK doesn’t exist if you didn’t use --cpus-per-task. And when you run a script with bash instead of sbatch, they either don’t exist, or, in a VS Code terminal at OSC, contain the values of your VS Code job (which is a Slurm job too!). When a variable doesn’t exist, set -u will make your script stop with an “unbound variable” error.

To avoid this, provide a default value using parameter expansion:

star.sh (excerpt)
#SBATCH --cpus-per-task=8

# Use the number of reserved cores, or 1 if $SLURM_CPUS_PER_TASK doesn't exist
cores="${SLURM_CPUS_PER_TASK:-1}"

STAR --runThreadN "$cores" --genomeDir [...]

You can also use these variables to record a job’s resources in its Slurm log file, which is useful when you look back at the log file later. For example, in the initial logging section of your script:

scripts/fastqc.sh (excerpt)
echo "Slurm job ID:       ${SLURM_JOB_ID:-none}"
echo "Number of cores:    ${SLURM_CPUS_PER_TASK:-1}"

4 Copying the Slurm log file to the output dir

In w10b, you moved your Slurm log files into a logs subdir of the output dir by hand, after checking them.

You may wonder why you shouldn’t simply include a dir in the --output path, e.g. #SBATCH --output=results/fastqc/logs/slurm-fastqc-%j.out, so that log files don’t have to be moved manually after the job has finished. But this has two disadvantages:

  • The dir must already exist when you submit the job.
    Slurm creates the log file when the job starts, before any line of your script has run, and it won’t create missing dirs for you. So, a mkdir -p line inside the script would come too late: the job would fail right away, and no log file would be created at all — leaving you with nowhere to look to find out what went wrong. You’d instead need a mkdir -p line right above your sbatch command(s) in your protocol Markdown file.

  • It’s good to do the manual work.
    When log files show up in your working dir, you’ll notice them, and that is a reminder to check them for errors before moving them to their final location. When they quietly end up elsewhere, it’s easier to forget about a job and never check whether it succeeded.

Instead, your script itself can put a copy of its Slurm log file in the output dir. The original log file will then still show up in your working dir, so you’ll notice it and check it — but afterwards, you can simply delete it, since a copy is already stored alongside the outputs. To do this, add the following lines to the very end of your script:

scripts/fastqc.sh (excerpt)
# Copy the Slurm log file to the output dir (only when running as a batch job)
if [[ "$0" == */slurm_script ]]; then
    log_file=$(scontrol show job "$SLURM_JOB_ID" | grep "StdOut=" | cut -d "=" -f 2)
    mkdir -p "$outdir"/logs
    cp "$log_file" "$outdir"/logs/
fi

How this works:

  • [[ "$0" == */slurm_script ]] checks whether the script runs as a batch job. $0 contains the path of the script that is running, and in a batch job, Slurm runs a copy of your script called slurm_script (which is why error messages in Slurm log files mention a path like /var/spool/slurmd/job37615711/slurm_script). (Checking whether $SLURM_JOB_ID exists wouldn’t work: it is also set in your VS Code terminal, because your VS Code session is a Slurm job.) See also this section on if statements.
  • scontrol show job prints information about a job, including a line StdOut=<path> with the path to its Slurm log file. grep selects that line, and cut extracts the part after the =. Because the path comes from Slurm, this works no matter how you named your log files with --output.

Two things to note:

  • Put these lines at the very end of the script, after the final “Successfully finished” logging lines, because the copy will only contain what was printed up to that point.
  • If the script fails, it stops before it reaches these lines (thanks to set -e), so no copy is made. That’s actually useful: copies in your output dirs only exist for jobs that succeeded, while the log files of failed jobs only end up in your working dir, where you’ll notice them.

5 Interactive shell jobs

Interactive shell jobs will grant you interactive shell access on a compute node. When you use the VS Code app in OnDemand, your terminal already runs in an interactive job on a compute node! And if you need more cores for that job, you can request them in the OnDemand form.

But when you work in a plain shell on a login node instead, for example when you connect to OSC with SSH from your own computer, you need to start an interactive shell job yourself before you can run anything substantial. You can do so with Slurm’s srun command1, to which you add --pty /bin/bash to get an interactive Bash shell.

To try this, open a login-node shell in OnDemand via Clusters > Pitzer Shell Access. Then, request an interactive shell job, e.g. with 5 cores for 2 hours:

srun --account=PAS3493 --cpus-per-task=5 --time=120 --pty /bin/bash
srun: job 56706630 queued and waiting for resources
srun: job 56706630 has been allocated resources
[jelmer@p0133 ~]$

First, some Slurm scheduling info was printed to screen: initially, the job was queued, and then it was “allocated resources”. Then, you got a new prompt, which shows the name of the compute node your job runs on (here, p0133, whereas before, the prompt showed a login node, like pitzer-login01). Any commands you now type will run in this job, with its 5 cores.

Don’t run srun from a VS Code terminal at OSC. Your VS Code session is a Slurm job itself, so srun will try to run inside that job instead of starting a new one. If you ask for more cores than your VS Code job has, it will keep printing “step creation temporarily disabled” (press Ctrl+C to stop it).

When you’re done, type exit to end the job and go back to your original shell. Otherwise, the job will keep running (and using your project’s compute hours) until it reaches its time limit.

6 Monitoring your jobs with squeue

6.1 Choosing which columns to show

The default columns of squeue -u $USER -l are quite narrow: for example, job names are cut off after 8 characters. That is a problem when you have many jobs with long names, such as the jobs that a Nextflow pipeline submits. With the --format option, you can choose which columns to show, and how wide they are:

squeue -u $USER --format="%.9i %.9P %.100j %.8T %.10M %.10l %.4C %R %.16V"
    JOBID PARTITION                                                                                                 NAME    STATE       TIME TIME_LIMIT CPUS NODELIST(REASON)      SUBMIT_TIME
 42175824       cpu                 nf-NFCORE_RNASEQ_RNASEQ_FASTQ_QC_TRIM_FILTER_SETSTRANDEDNESS_SORTMERNA_(S79)  RUNNING       0:53   16:00:00   17 p0111 2026-11-30T08:49
 42175780       cpu          nf-NFCORE_RNASEQ_PREPARE_GENOME_STAR_GENOMEGENERATE_(GCF_016801865.2_TS_CPP_V2_genomic.fna)  RUNNING       3:19   16:00:00   17 p0116 2026-11-30T08:46
 42175708       cpu                                                                                        nfc-rnaseq.sh  RUNNING       5:19   12:00:00    1 p0222 2026-11-30T08:44

Each % code in the --format string is one column, and the number before the letter sets the column’s width: for example, %.100j shows the job name in a 100-character-wide column. (The . makes the text right-aligned.) These are the codes used above, plus a few other useful ones:

Code Column
%i Job ID
%P Partition
%j Job name
%T Job state (e.g. PENDING or RUNNING)
%M For how long the job has been running
%l Time limit
%C Number of reserved cores
%R When running: the node(s) it runs on;
when pending: why it is pending
%V When the job was submitted
%m Amount of reserved memory
%S When the job started, or for pending jobs, when it is expected to start

For a full list of codes, see the --format section in the manual (man squeue).

6.2 Other useful squeue options

  • To see when your pending jobs are expected to start, use --start (Slurm’s estimates are often rough, and may change as other jobs are submitted):

    squeue -u $USER --start

  • To count your jobs, for example how many of them are still pending, combine -t with -h (no header line) and wc -l:

    squeue -u $USER -t PENDING -h | wc -l

  • To only show specific jobs, use -j with one or more job IDs, e.g. squeue -j 42175708,42175780.

To avoid having to type the long --format command, you can make an alias for it.

7 Checking your jobs’ resource usage

To choose sensible values for --time, --mem, and --cpus-per-task, it helps to know how much of each your earlier jobs actually used. For example, after running a program for one or a few samples, you can use this information to adjust the requests for the remaining samples.

7.1 seff: resource usage of a finished job

The easiest way to check a job’s resource usage is with seff (“Slurm efficiency”), which takes a job ID as its only argument:

seff 37615718
Job ID: 37615718
Cluster: pitzer
User/Group: jelmer/PAS0471
State: COMPLETED (exit code 0)
Cores: 1
CPU Utilized: 00:00:08
CPU Efficiency: 80.00% of 00:00:10 core-walltime
Job Wall-clock time: 00:00:10
Memory Utilized: 245.32 MB
Memory Efficiency: 5.38% of 4.45 GB

The most useful lines are:

  • State — whether the job completed successfully (see the section on sacct for other states).
  • CPU Efficiency — how much of the reserved cores’ time was actually used. A low percentage for a job with multiple cores means that the program didn’t use all of them. For example, a FastQC job for a single file with 4 cores would get no more than 25%: recall the FastQC exercise in w10b.
  • Memory Utilized — the peak memory use, which Memory Efficiency compares to the amount of memory you had available. If a job failed and this is close to 100%, it likely ran out of memory.
  • Job Wall-clock time — how long the job ran, which you can compare to the time limit you set with --time.

Only use seff after a job has finished: for running jobs, the numbers are incomplete.

Noteosc-seff for GPU jobs

OSC also has its own version of this command, osc-seff, which additionally reports GPU usage for jobs that used GPUs.

7.2 sacct: an overview of many jobs

When you’ve submitted many jobs, sacct gives you a table with one row per job, including jobs that have already finished:

sacct -X
JobID           JobName  Partition    Account  AllocCPUS      State ExitCode
------------ ---------- ---------- ---------- ---------- ---------- --------
37615614     ondemand/+        cpu    pas0471          1    RUNNING      0:0
37615705       sleep.sh        cpu    pas0471          1    TIMEOUT      0:0
37615718      fastqc.sh        cpu    pas0471          1  COMPLETED      0:0
37615719      fastqc.sh        cpu    pas0471          1  COMPLETED      0:0
37615720      fastqc.sh        cpu    pas0471          1     FAILED      1:0
# [...output truncated...]
  • By default, sacct shows your own jobs that started since midnight. To go back further, use --starttime, e.g. --starttime=2026-10-26.
  • -X (--allocations) shows one line per job. Without it, each job also gets lines for its “job steps”, like .batch and .extern.
  • For a single job, use -j, e.g. sacct -X -j 37615720.

These are the most common values in the State column:

State Meaning
COMPLETED The script finished with exit status 0 (no error)
FAILED The script stopped with an error (see the ExitCode column)
TIMEOUT The job was killed because it reached its time limit
OUT_OF_MEMORY The job was killed because it reached its memory limit
CANCELLED The job was canceled, e.g. with scancel
TipAnother reason to use set -e

A shell script’s exit status is that of the last command it ran. So, without set -e, a script in which a command fails halfway may still end with exit status 0, and Slurm would list the job as COMPLETED. With set -euo pipefail, the script stops at the failing command, and the job is correctly listed as FAILED.

To list only the jobs that did not succeed, use --state. In that case, you always have to specify --starttime too — otherwise, sacct only lists jobs that are in one of these states right now:

sacct -X --starttime=2026-10-26 --state=FAILED,TIMEOUT,OUT_OF_MEMORY,CANCELLED
JobID           JobName  Partition    Account  AllocCPUS      State ExitCode
------------ ---------- ---------- ---------- ---------- ---------- --------
37615705       sleep.sh        cpu    pas0471          1    TIMEOUT      0:0
37615720      fastqc.sh        cpu    pas0471          1     FAILED      1:0

Finally, you can choose which columns to show with --format. For example, to add a column with each job’s run time (Elapsed), and to make the JobName column wider so that long job names are not cut off:

sacct -X --format=JobID,JobName%15,State,ExitCode,Elapsed
JobID                JobName      State ExitCode    Elapsed
------------ --------------- ---------- -------- ----------
37615614     ondemand/sys/d+    RUNNING      0:0   00:21:32
37615705            sleep.sh    TIMEOUT      0:0   00:01:11
37615718           fastqc.sh  COMPLETED      0:0   00:00:10
37615719           fastqc.sh  COMPLETED      0:0   00:00:11
37615720           fastqc.sh     FAILED      1:0   00:00:02
# [...output truncated...]
  • Column names are separated by commas, without spaces.
  • %15 after a column name sets that column’s width to 15 characters (by default, most columns are 10 characters wide, which is why the name of the OnDemand job was cut off to ondemand/+ above).

7.3 sstat: running jobs

seff and sacct only give complete information after a job has finished. To check the memory use of a job while it is running (e.g. if you’re worried that it may run out of memory), use sstat:

sstat -j 37615800.batch --format=JobID,MaxRSS,AveCPU
JobID            MaxRSS     AveCPU
------------ ---------- ----------
37615800.ba+   2405304K   00:02:19

Here, MaxRSS is the peak memory use so far. Note the .batch after the job ID: sstat reports on job “steps”, and the main step of a batch job is called batch.

7.4 Aliases for long job monitoring commands

Because you won’t remember all of these formatting options, and even if you do, you don’t want to type them out, this is a case where aliases are really handy. For instance:

alias sq='squeue -u $USER --format="%.9i %.9P %.100j %.8T %.10M %.10l %.4C %R %.16V"'
alias sact='sacct -X --format=JobID,JobName%15,State,ExitCode,Elapsed'
alias sst='sstat --format=JobID,MaxRSS,AveCPU'

You can then add other options when you use an alias, for example:

sq -t PENDING
sact -j 123456
sst -j 123456.batch

An alias only lasts for the current shell session, so to make them always available in interactive sessions, add the lines to your Bash configuration file ~/.bashrc. See the page on configuring your shell for more on ~/.bashrc and aliases.

Aliases are not available in scripts, so make sure to write out the full commands in scripts (e.g. your Slurm batch job scripts).

7.5 /usr/bin/time and $SECONDS in a script

To measure the run time and peak memory use of a single command in a script, put /usr/bin/time in front of it. Its -f option sets what to report, and -o writes the report to a file. For example, %E is the run time and %M the peak memory use in KB:

scripts/fastqc.sh (excerpt)
# Run FastQC, and store its run time and peak memory use in a file:
/usr/bin/time -f "%E %M" -o "$outdir"/time.txt \
    apptainer exec "$CONTAINER" fastqc --outdir "$outdir" "$fastq"

# Print the run time, and the peak memory use converted from KB to GB:
awk '{printf "Run time: %s    Peak memory: %.2f GB\n", $1, $2 / 1024 / 1024}' "$outdir"/time.txt

This will add a line like the following to your Slurm log file:

Run time: 0:09.85    Peak memory: 0.24 GB

(The awk command reads the two numbers from the file, and prints them with some text, dividing the memory by 1024 twice to go from KB to GB: see the awk section of the self-study page on shell data tools to learn more. And to get a long list of statistics, use /usr/bin/time -v instead.)

Use the full path /usr/bin/time rather than just time: plain time runs a simpler, built-in Bash version that can’t report memory use and doesn’t have the -f and -o options.

Finally, to report how long your whole script took to run, you can use $SECONDS: a special Bash variable that contains the number of seconds since the script started. For example, add this line to the end of your script:

scripts/fastqc.sh (excerpt)
echo "This script ran for $SECONDS seconds"

8 Automating multi-step workflows

In w10b, you saw that you can’t run all the code in a Markdown protocol at once, because most steps need the output of an earlier step. This section shows a few ways to automate such a workflow further with Bash and Slurm. But keep in mind that each of them makes your scripts more complex, and that a workflow management system like Nextflow is often a better investment of your time.

8.1 Combining steps in one script

At the extreme, you could write a single shell script with a loop for each step, and submit it as a single batch job. While this would work, it would be inefficient: the sample-wise steps would run one sample after the other, instead of simultaneously in separate batch jobs.

A more reasonable approach is to write scripts that process one sample, but run as many steps as possible for that sample. However, what if you need to redo only the steps from the middle of your workflow onwards, e.g. because you want to change some settings there? Rerunning your all-inclusive script would mean rerunning all steps, which could be a big waste of time.

if statements

You could overcome this with if statements that only run certain steps, for example:

scripts/trim_and_map.sh (excerpt)
# Copy the placeholder variables
fastq_r1="$1"
fastq_r2="$2"
run_trim="$3"   # true or false
run_map="$4"    # true or false

# Step 1: Read trimming
if [[ "$run_trim" == true ]]; then
    bash scripts/trim.sh "$fastq_r1" "$fastq_r2" results/trim
fi

# Step 2: Mapping the trimmed reads
if [[ "$run_map" == true ]]; then
    trimmed_r1=results/trim/$(basename "$fastq_r1")
    trimmed_r2=results/trim/$(basename "$fastq_r2")
    bash scripts/map.sh "$trimmed_r1" "$trimmed_r2" results/map
fi

Then, to only rerun the mapping step for a sample:

sbatch scripts/trim_and_map.sh \
  data/fastq/S63_R1.fastq.gz data/fastq/S63_R2.fastq.gz false true

To learn more about if statements, see this section of the self-study page on shell scripting.

Script options

As you can see above, it quickly becomes hard to tell what each “positional” argument (like $3 and $4) means, and it’s easy to mix them up. Instead, you can write your script such that it accepts options, e.g.:

sbatch scripts/trim_and_map.sh \
  --skip_trim data/fastq/S63_R1.fastq.gz data/fastq/S63_R2.fastq.gz

To learn how to do this, see this section of the self-study page on shell scripting.

8.2 Slurm job dependencies

With the --dependency option, you can submit all jobs at once, but tell Slurm that a job should only start after the jobs whose outputs it needs have successfully finished. For that, you need the job IDs of those earlier jobs. The --parsable option makes sbatch print only the job ID (instead of Submitted batch job <job-id>), which you can store in a variable with command substitution:

map_ids=""

for fastq_r1 in data/fastq/*_R1.fastq.gz; do
    fastq_r2=${fastq_r1/_R1/_R2}

    # Submit the trimming job and store its job ID:
    trim_id=$(sbatch --parsable scripts/trim.sh "$fastq_r1" "$fastq_r2" results/trim)

    # Submit the mapping job, which will only start once the trimming job
    # has successfully finished (`afterok`), and store its job ID too:
    trimmed_r1=results/trim/$(basename "$fastq_r1")
    trimmed_r2=results/trim/$(basename "$fastq_r2")
    map_id=$(sbatch --parsable --dependency=afterok:"$trim_id" \
        scripts/map.sh "$trimmed_r1" "$trimmed_r2" results/map)

    # Add the mapping job ID to a colon-separated list of all of them:
    map_ids="$map_ids:$map_id"
done

# The counting job will only start once ALL mapping jobs have successfully finished:
sbatch --dependency=afterok"$map_ids" scripts/count.sh results/map results/count_table.txt

If a job fails, the jobs that depend on it will never start. They may remain in the queue as PENDING, with DependencyNeverSatisfied as the reason, until you cancel them with scancel.
