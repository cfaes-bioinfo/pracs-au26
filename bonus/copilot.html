1 Introduction

In class, we used the Claude extension in VS Code Server (see the week 9 lecture). Claude is great for chat and agent-style help, but it does not give you code completions: AI suggestions that appear in the editor as you type. Additionally, you can only continue to use Claude after this course if your PI supports an Ohio State Generative AI account, or if you get a personal account1.

This page focuses on GitHub Copilot, which in VS Code is a built-in feature. Here is how it compares to Claude Code (as also shown in the week 8 slides):

Feature GitHub Copilot Claude Code
Code completions ✅ ❌
Agentic chat ✅ ✅
Free use with a personal, “academic” account ✅ 2 ❌
Can be paid for with university funds ❌ ✅
Approved for use with institutional data ❌ ✅
Often considered the best AI coding tool ❌ ✅

On this page, you will learn how to:

  • Get free extended access to GitHub Copilot as a student
  • Sign in to GitHub Copilot and enable its code completions in VS Code
  • Use GitHub Copilot’s code completions, inline chat, and chat to help you with coding tasks

As pointed out in the table above: unlike the Claude setup we use in class, GitHub Copilot is not an OSU-approved tool. This is true even though the similarly named Microsoft Copilot is OSU-approved: these are separate products from the same company3. So, whenever you use GitHub Copilot, you must be aware of the data privacy implications outlined in the week 8 lecture.

3 Intro to code completions

3.1 What are code completions?

“Code completions ”, also known as “code suggestions” or, in VS Code, “inline suggestions”, are suggestions for additional or modified code (or other text) that Copilot shows right in the editor as you type. There are two types of code completions:

  • Ghost text suggestions add new code at your cursor.
  • Next edit suggestions change code that you have already written.

We’ll go over these one by one. After that, we’ll turn to Copilot’s chat, and in an appendix, to inline chat, a related feature that also works right in the editor.

Finally, create a file copilot.sh, and open it in the editor. If Copilot is active, you should see some ghost text startup suggestions in the file already:

To run the code in your file, you can either copy it to the terminal and press Enter, or use a keyboard shortcut to send the code from the editor to the terminal. You should have set up that shortcut in week 7, but if not, see the next box for instructions.

NoteWhy a .sh file instead of a Markdown file? (Click to expand)

In other sessions, you’ve been typing code in a Markdown file and sending it to the terminal from there. Here, we’ll use a file with a .sh extension instead, because that makes things a bit easier with Copilot:

  • In a .sh file, Copilot knows that everything is Bash code, so it will suggest code rather than prose, and comment lines work as prompts.
  • You don’t need to create code blocks with backticks.

But note that this file is not a real shell script like the ones you wrote in week 7: it is a scratch file whose lines you run one by one in the terminal, just like the code in your Markdown files. You won’t run it with bash or sbatch, which is why it doesn’t need a shebang line or set settings.

This shortcut will send selected code in the editor to the terminal. When no text is selected, the shortcut sends the line your cursor is on (in VS Code, your entire line is implicitly “selected” when your cursor is on it). To run a multi-line command like a for loop, first select all of its lines.

  2. Type “Run Selected Text” in the search box, and you should see the option “Terminal: Run Selected Text in Active Terminal”.

4 Ghost text suggestions

Ghost text suggestions are the most common type of code completions. As you type, Copilot shows a suggestion in light gray “ghost text”. Press Tab to accept it, or Esc to dismiss it (you can also simply keep typing, which dismisses it too). There are two kinds of ghost text suggestions.

4.1 Completing what you’re typing

These suggestions try to complete the line you are typing, or suggest a next line based on the previous ones. For example, if you type #! in the first line of copilot.sh, it’s likely that Copilot will suggest the rest of the shebang line:

I typed #!, and Copilot suggested /bin/bash in ghost text.
It can be a little hard to see the distinction, but the ghost text is fainter than the already typed text.

When you accept the suggestion with Tab, the line is completed. And it may immediately suggest a next line:

Here, Copilot suggested echo "Hello, world!" as a next line.

Press Esc to dismiss the suggestion, whatever it is.

NoteNot just code: an example in a Quarto document (Click to expand)

Copilot can help with many kinds of text, not just code. In a Quarto document that is part of the source code of this website, I typed the Markdown syntax to insert an image, ![](/img/claude-interrupt1.png){}, and Copilot then suggested the part in gray:

4.2 A comment as a prompt

These suggestions generate code that tries to implement what you described in a comment line. This is similar to asking a question in the chat, but can be faster and more convenient for small tasks, while less suitable for more complex questions.

Let’s try this in your copilot.sh file. First, add the following into it:

copilot.sh
# GTF file:
GTF=data/annot.gtf

A first example

When you go to a new line and wait a second, you may already see a ghost text suggestion that acts on the GTF variable. But instead of letting GitHub Copilot go off on its own to randomly suggest ways to interrogate the GTF file, let’s give it a “prompt” by typing a comment line first:

copilot.sh (excerpt)
# Count the number of entries in the GTF file

You may see a ghost text suggestion appear even with your cursor still at the end of the line, but otherwise, press Enter to go to a new line, and wait for a second for the suggestion to appear. Accept it with Tab and run the code: does it seem to have given a correct suggestion?

“Entries” means rows in the table part of the GTF file, i.e. excluding the header lines that start with #, but this is deliberately a little vague, so Copilot may not always get it right. For example, it may suggest a command that simply counts all lines instead. In that case, you could switch the prompt comment to:

copilot.sh (excerpt)
# Count the number of entries (non-header lines) in the GTF file

A correct answer may well look like this — recall, you can use grep -v to exclude lines that start with # (“starts with” is expressed as ^ in a regular expression; not covered in class), and then pipe the result into wc -l to count the lines:

Tips and pitfalls

  • Overall, mistakes are much more likely here than in the (Claude Code) chat, because it will use a low-tier model, and sometimes also because it has less context to work with. For example:

    This suggestion is wrong, because the string gene can occur in many lines
    that do not represent a gene-level feature in the GTF file.

    You can follow up with a comment asking Copilot to fix the command, and it may do so.

  • Sometimes, multiple suggestions are available for a prompt, and you can hover over the ghost text to see them.

  • After you’ve accepted and run a command, go to a new line, type only a comment symbol (#), and wait: Copilot will often suggest a next step that builds on the previous command. See where that leads you, and whether it makes sense!

  • Think of something you want to do, start typing the command yourself, and see if and how Copilot completes it.

5 Next edit suggestions

“Next edit” suggestions suggest a change to code or other text that you have already written. Several kinds of situations can trigger next edit suggestions, such as:

  • Syntax, spelling, or style errors in your code, such as a missing closing bracket or quote.
  • Changing one instance of a recurring pattern in your code, such as a variable name or a path: Copilot will then suggest to change the other instances as well.

(There isn’t always a bright line between these two kinds of situations.)

5.1 Fixing errors

As a very simple example of the first kind, type the incorrect Ls -lh in your copilot.sh file, and wait a second: Copilot should suggest changing it to ls -lh, with a lowercase l:

Ls is incorrect, and Copilot recognizes that we are looking for ls instead.
As always, press Tab to accept the suggestion.

5.2 Recurring patterns

When you change one instance of a recurring pattern, such as a sample ID, a variable name, or a file name, Copilot will often suggest changing the other instances as well. We’ll go through two examples.

A shell script for a single sample

Create a new file fastq_summary.sh, and paste the following script into it. This script summarizes the FASTQ files for sample S63 (you don’t need to run it):

fastq_summary.sh
#!/bin/bash
set -euo pipefail

# Summarize the FASTQ files for sample S63
R1=../garrigos/fastq/S63_R1.fastq.gz
R2=../garrigos/fastq/S63_R2.fastq.gz
outdir=results/fastq_summary/S63

mkdir -p "$outdir"

# Count the number of lines in each FASTQ file
n_R1=$(zcat "$R1" | wc -l)
n_R2=$(zcat "$R2" | wc -l)

# Write the line counts to a TSV file
echo -e "S63\tR1\t$n_R1" > "$outdir"/S63_counts.tsv
echo -e "S63\tR2\t$n_R2" >> "$outdir"/S63_counts.tsv

# Save the first read of each file
zcat "$R1" | head -n 4 > "$outdir"/S63_R1_first-read.txt
zcat "$R2" | head -n 4 > "$outdir"/S63_R2_first-read.txt

echo "Done with sample S63"

Let’s say that you now want to summarize the FASTQ files for sample S64 instead. Change S63 to S64 in the line that starts with R1=, and wait a second: Copilot is likely to suggest changing the next instance as well. Press Tab to accept a suggestion, Tab again to move on to the next suggestion, Tab again to accept that one, and so on. Did Copilot catch all instances of S63, including the ones in the comment line and in the final echo command?

A better solution would be to make the script work for any sample, by having it accept the sample ID as an argument, as you learned in week 7. To do so, first add the line sample_id=$1 above the R1= line. Then, change the R1= line to:

R1=../garrigos/fastq/${sample_id}_R1.fastq.gz

Copilot should now suggest replacing the other hard-coded sample IDs with ${sample_id} as well. Check its suggestions carefully: for example, does it keep the curly braces in ${sample_id}_counts.tsv? Without them, the shell would look for a (nonexistent) variable sample_id_counts.

An R script

Next edit suggestions are not limited to changing identical pieces of text. The R script below uses the built-in iris dataset to summarize, plot, and test the sepal length of three iris species. Even if you don’t know R yet, you should be able to follow along. Create a new file iris.R, and paste the following code into it (again, you don’t need to run it):

iris.R
library(ggplot2)

# Mean sepal length per species
aggregate(Sepal.Length ~ Species, data = iris, FUN = mean)

# Boxplot of sepal length per species
p <- ggplot(iris, aes(x = Species, y = Sepal.Length)) +
  geom_boxplot() +
  labs(y = "Sepal length (cm)", title = "Sepal length by species")
ggsave("sepal_length_boxplot.png", p)

# Test whether sepal length differs between versicolor and virginica
iris_sub <- subset(iris, Species != "setosa")
t.test(Sepal.Length ~ Species, data = iris_sub)

Note that sepal length is referred to in four different ways in this script: “sepal length” in the comments, Sepal.Length as the column name, “Sepal length” in the plot labels, and sepal_length in the file name. So, if you wanted to switch to a different variable, a single find-and-replace wouldn’t do the trick.

Change “sepal length” to “petal width” in the first comment line, and see whether Copilot suggests changing Sepal.Length to Petal.Width in the next line. Keep pressing Tab to see if it also updates the plot labels, the output file name, and the other comment lines.

This works in the other direction, too: change geom_boxplot() to geom_violin() to make a violin plot instead, and see whether Copilot suggests updating the “Boxplot” comment and the _boxplot.png part of the file name.

TipCode completions and your data

Code completions mainly use the file you’re working in, and other open files, as context. So if you use them only in your code and documentation files, and don’t open data files while doing so, you are unlikely to send any of your data to GitHub, even if your workspace contains data files. This is different for the chat, especially in Agent mode (see below): an agent can read any file in your workspace, and the output of the commands it runs.

6.2 Approval levels

The approval levels are similar to Claude’s permission modes, but not equivalent. The available approval levels are:

  • Default Approvals falls between Claude’s Manual and Edit automatically modes. Like in Manual mode, Copilot runs common read-only commands without asking, and asks for permission before running other commands. But like in Edit automatically mode, it doesn’t ask before editing files in your workspace (except for “sensitive” files like settings files): it saves its edits right away, and you can then keep or undo each one.

  • Bypass Approvals lets Copilot do everything without asking, including running any command. But it still works like a regular chat turn: it may stop to ask you a question, or stop when it runs into an error.

  • Autopilot goes one step further: besides doing everything without asking, it also answers its own questions, and retries on errors, so it keeps going until it decides the task is done.

The approval level menu, with “Default Approvals” selected.

Note that neither Bypass Approvals nor Autopilot has the AI safety check that Claude’s Auto mode has: they really skip all approvals, including for destructive commands4. (And whereas Plan is one of Claude’s permission modes, it is one of the chat modes in Copilot: see below.)

NoteThe Local button (Click to expand)

The Local button below the box sets where the agent runs. You’ll only need the default, Local, which runs it right here in VS Code on your own files. The other options hand the task off to a separate agent that works in the background: Copilot CLI runs Copilot’s command-line agent on the machine where VS Code runs (here, at OSC), Cloud runs Copilot on GitHub’s servers (and opens a pull request with its changes), and Claude uses Anthropic’s Claude agent instead of Copilot’s own.

6.3 File context

Just like Claude, Copilot can search and read files in your workspace (the folder open in VS Code) by itself. And like in Claude, you can point it to specific files:

  • The file that’s active in the editor is suggested as context. Assuming you still have it open, you should see copilot.sh at the top of the chat box as shown in the screenshot on the right. However, unlike in Claude, it is not added automatically: click the + button next to the file name to add it.
  • Other files can be added with the + button at the bottom left of the chat box, or by typing # followed by part of a file name (in Claude, you used @ for this).
  • Lines of code that you select in the editor are added as context, just like in Claude.
TipFile/context tips

As with Claude, it’s often better to point Copilot to the relevant files explicitly, rather than letting it search for them. Even if not explicitly pointed to, Copilot is more likely to pay attention to the files you have open in the editor, so when asking questions, consider opening relevant files and closing irrelevant ones.

6.4 Modes

The second button from the left at the bottom of the chat box lets you select different chat modes5. The button will show the currently selected mode, which is usually Agent by default. Click it to see the menu with the three built-in modes:

The options in the modes/agents menu.

  1. Ask — Copilot answers questions, but doesn’t change any files or run any commands. Claude doesn’t have a mode like this, which is why we recommended using a browser-based chat for general questions.
  2. Agent — Copilot can search your files, create and edit files, and run commands. This is the mode that is most similar to how we used Claude in class.
  3. Plan — Just like Claude’s Plan mode, Copilot looks around your files without changing them, and writes a plan for a bigger task. Once you’re happy with the plan, Copilot switches to Agent mode to carry it out.

(The last item in the dropdown, Configure Custom Agents…, lets you create your own modes, each with its own instructions and a list of tools it may use — for example, a “reviewer” mode that can only read your files and comment on your code. You won’t need this for now, as the three built-in modes cover most use cases.)

6.5 Models

While Claude can only use Anthropic models, GitHub Copilot lets you choose between LLMs from different providers, like GPT, Claude, Gemini, and others.

However, on the Free and Student plans, you can only use whatever model Copilot automatically picks for each request — there’s no model dropdown to choose from. (Pro and other paid Copilot plans do let you manually pick a specific model.)

7.1 An example in “Ask” mode

Ask mode is most useful when you want Copilot to look at your files, but not change anything or run commands. For example, you can ask it to explain what a script does, why a certain line in it fails, or which of your scripts creates a certain output file. In Agent mode, Copilot may start editing files or running commands when all you wanted was an explanation.

To keep this first example simple, well ask a general question that doesn’t involve your files (just note that in your actual research, such questions may be better asked to Gemini, so you don’t use up your Copilot credits). Select “Ask” mode and type the following prompt:

In a Bash script with set -euo pipefail, why could the line zcat sample.fastq.gz | head -n 8 make my script stop with an error, even though the FASTQ file is fine?

Does its explanation make sense to you?

Click to see a possible answer

Here’s the answer I got from Copilot:

With set -euo pipefail, the pipeline’s exit status is treated as a failure if any command in it fails.

In:

zcat sample.fastq.gz | head -n 8

what often happens is:

  1. head -n 8 reads 8 lines, then exits normally (0).
  2. The pipe closes because head is done.
  3. zcat is still writing, gets SIGPIPE (broken pipe), and exits non-zero (commonly 141).
  4. Because of pipefail, the pipeline status becomes non-zero.
  5. Because of -e, your script exits.

So the FASTQ can be perfectly fine; it’s a broken-pipe side effect from intentionally truncating output with head.

Typical fixes:

  1. Ignore that specific pipeline failure:

    zcat sample.fastq.gz | head -n 8 || true

  2. Temporarily disable pipefail around this command:

    set +o pipefail
zcat sample.fastq.gz | head -n 8
set -o pipefail

  3. Use a command that can stop decompressing cleanly for small previews (depends on tools available), but the above is the common practical fix.

Most robust pattern in strict-mode scripts is to explicitly allow this known benign case.

Be careful with Copilot’s first suggested fix, || true

|| means “or”: the command after it only runs if the command before it fails. And true is a command that does nothing except succeed. So, adding || true to a line makes it “succeed” no matter what went wrong.

That solves the problem above, but if the FASTQ file were missing or corrupt, your script would now also carry on as if nothing happened — exactly what set -e is meant to prevent. This is a common pattern in AI suggestions: a fix that makes the error go away, but also hides errors you’d want to see.

NoteTesting Copilot’s explanation (Click to expand)

Unlike an agent, Ask mode won’t test its own claims — but you can easily do that yourself. $? contains the exit status of the last command: an exit status of 0 means success, and anything else means failure.

First, run the command without pipefail, which is the default in the shell:

zcat ../garrigos/fastq/S63_R1.fastq.gz | head -n 8
echo $?

After the 8 lines of the FASTQ file, you should see:

0

Then, run it again with pipefail turned on (set +o pipefail turns the setting off again at the end):

set -o pipefail
zcat ../garrigos/fastq/S63_R1.fastq.gz | head -n 8
echo $?
set +o pipefail

This time, after the FASTQ lines, you should see:

141

Without pipefail, the exit status of a pipeline is that of its last command, head, which ran successfully. With pipefail, a failure of any command in the pipeline becomes the exit status of the whole pipeline. Here, 141 means that zcat was killed by a “SIGPIPE” signal because head stopped reading after 8 lines. In a script with set -e, that would make the script stop at this line.

When I asked it this, Copilot already suggested a few ways to avoid the problem, but if it didn’t, you could ask it a follow-up question, like “How can I avoid this?”. You could also ask it to further explain something it said, or to give a simpler explanation.

TipWhy “not awk”? And thoughts on providing constraints. (Click to expand)

For tasks with tabular files like GTF files, AI tools tend to use awk, a powerful command that is really its own language, and that we haven’t covered in this course other than briefly this optional self-study section.
