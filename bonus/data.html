1 Introduction

This page contains additional notes on project and data management: sharing data and code across projects, symbolic links, checking file integrity with checksums, file permissions, and more about file compression. (For transferring files to and from OSC, see the SSH and file transfer page, and for downloading genomes and reads from NCBI, see the Finding and downloading data from NCBI reference page.)

Run the commands on this page from your personal dir, /fs/ess/PAS3493/people/$USER, and follow the sections in order, since some of them change your working dir.

2 When projects share data and/or code

We’ve talked about organizing your work into projects, and keeping each project self-contained. But what if you have related projects that share data and/or code?

From Wilson et al. (2017):

As a rule of thumb, divide work into projects based on the overlap in data and code files:

  • If 2 research efforts share no data or code, they will probably be easiest to manage independently.

  • If they share more than half of their data and code, they are probably best managed together.

  • If you are building tools that are used in several projects, the common code should probably be in a project of its own.

To access files that are outside of the project, because they are shared across projects, one solution is to create links (i.e. shortcuts/aliases) to these files (see below for how to do this):

But in many cases, it may be better to store shared data and/or scripts in separate folders altogether, and link to them in each project that uses them:

Both of the above strategies do decrease the portability of your project, and moving the shared files even within your own computer will cause links/shortcuts to break. A more portable method is to keep shared (multi-project) files online — this is especially feasible for scripts under version control:

For data, this is also possible but often not practical due to file sizes. It’s easier after data has been deposited in a public repository.

3 Symbolic links

As shown above, a convenient way to use files that are stored outside of a project is with symbolic links (“symlinks”): small files that merely point to another file or dir, much like a shortcut (Windows) or alias (Mac).

mkdir -p sandbox
cd sandbox

3.1 Symlinks to files

You can create a symlink with ln -s:

  • When you only provide the source file or dir, it creates a link of the same name in your working dir:

    ln -s /fs/ess/PAS3493/data/garrigos/fastq/S64_R1.fastq.gz
    ls -l
    lrwxrwxrwx 1 jelmer PAS0471 51 Nov  5 10:12 S64_R1.fastq.gz -> /fs/ess/PAS3493/data/garrigos/fastq/S64_R1.fastq.gz

  • You can also give a path to the link, such as simply a different name:

    ln -s /fs/ess/PAS3493/data/garrigos/fastq/S64_R1.fastq.gz shared.fastq.gz
    # Both the first link and the new link are now in your working dir:
ls -l
    lrwxrwxrwx 1 jelmer PAS0471 51 Nov  5 10:12 S64_R1.fastq.gz -> /fs/ess/PAS3493/data/garrigos/fastq/S64_R1.fastq.gz
lrwxrwxrwx 1 jelmer PAS0471 51 Nov  5 10:12 shared.fastq.gz -> /fs/ess/PAS3493/data/garrigos/fastq/S64_R1.fastq.gz

Above, you could see that in the long-format ls output, symlinks start with an l and show their target after the ->.

Once you have a symlink, you can use it like the original file. For example:

zcat shared.fastq.gz | head -n 2
@ERR10802864.1 1 length=71
GATCAACCATGCAGCTGCCAGGTGGTGGCCACTTCCGGCTGCACCACACCGACCAGATTTGTTGCCCGGGC
WarningAbsolute or relative paths for the source? (Click to expand)

Above, you may have noticed that we used the absolute path to the source file. This is not strictly necessary, but it is safer than using a relative path. If you use a relative path for the source, it is interpreted relative to the location of the link, not to your working dir. For example, running the following from your personal dir creates a broken link, because it points to sandbox/garrigos/README.md, which doesn’t exist:

ln -s garrigos/README.md sandbox/

The easiest way to avoid this is to use absolute paths for the source, e.g. with the $PWD variable, which contains your working dir:

# Also run from your personal dir:
ln -s "$PWD"/garrigos/README.md sandbox/

That said, relative links have the advantage of relative paths that you learned about in w11a: a relative link between two files in the same project keeps working when you move or share the whole project. For example, this would create a working relative link (also run from your personal dir):

ln -s ../garrigos/README.md sandbox/

So, use absolute paths for links to files outside of your project (like shared data), and consider relative ones for links within a project.

3.2 Symlinks to dirs

You can link to a dir in the same way. For example, create a link to the dir with the Garrigos et al. FASTQ files:

ln -s /fs/ess/PAS3493/data/garrigos/fastq fastq-link

A symlink to a dir is a point of entry to the original dir: anything you do through the link affects the original files. For example, listing the link’s contents shows the files in the original dir:

ls fastq-link | head -n 2
S63_R1.fastq.gz
S63_R2.fastq.gz

So, rm fastq-link/*.fastq.gz would remove the original FASTQ files!

Alternatively, you can link to each of the files in a dir at once with a wildcard. This creates separate links to the files instead of a single link to the dir:

# Link to a dir: creates a link 'project1/scripts/shared_scripts':
ln -s /fs/ess/PAS3493/shared_scripts project1/scripts/

# Link to each of the files in a dir:
ln -s /fs/ess/PAS3493/shared_scripts/* project1/scripts/

3.3 Removing symlinks

To remove a symlink, use rm or unlink. This only removes the link itself, not the file or dir it points to. For example, remove the two file links you created above:

rm shared.fastq.gz
unlink S64_R1.fastq.gz

Removing these symlinks did not affect the original file, which is still there:

ls /fs/ess/PAS3493/data/garrigos/fastq/S64_R1.fastq.gz
/fs/ess/PAS3493/data/garrigos/fastq/S64_R1.fastq.gz

To remove a link to a dir, also use rm without -r (the link is a file, even when it points to a dir):

rm fastq-link
WarningWatch out for trailing slashes

rm -r fastq-link only removes the link, but rm -r fastq-link/ (with a trailing slash, which tab completion may add) follows the link and removes the contents of the original dir!

4 Checking file integrity with checksums

When you receive FASTQ files from a sequencing facility, or download files from a public repository, they are often accompanied by a small text file with a name like md5.txt, md5checksums.txt, or sha256sums.txt.

Such a file contains so-called checksums, a sort of digital fingerprint for files, which you can use to check whether your copy of these files is completely intact (e.g., that a transfer didn’t get cut short).

A checksum is a short string computed from a file’s contents, in such a way that if even one character in the file changes, the checksum will be completely different. For example, you can compute an md5 checksum with the md5sum command — here, for a string of text rather than a file:

echo "bioinformatics is fun" | md5sum
010b5ebf7e207330de0e3fb0ff17a85a  -
echo "bioinformatic is fun" | md5sum
45cc2b76c02b973494954fd664fc0456  -

Note that the two strings differ by only one character, but their checksums are completely different.

(The - above means that md5sum read its input from standard in rather than from a file.)

4.1 Checking a downloaded file

Downloads, especially of large files, can occasionally be cut short or end up incomplete, for example when the network connection drops. This won’t always produce a clear error, and an incomplete file can look perfectly normal at first glance: its name is the same, and the first lines look fine. Checking the checksum is the way to be sure that you got the whole file.

The NCBI FTP dir with the Culex pipiens genome files that you downloaded from in week 11 also contains a checksum file, md5checksums.txt. Download it into your week11/sandbox dir, where you downloaded the protein FASTA file in the w11a exercise1:

# Move back from 'sandbox' to your personal dir
cd ..
wget -P week11/sandbox https://ftp.ncbi.nlm.nih.gov/genomes/all/GCF/016/801/865/GCF_016801865.2_TS_CPP_V2/md5checksums.txt

The file has one line per file in the FTP dir, with the checksum in the first column and the file name in the second. Let’s look up the line for the protein FASTA file:

cd week11/sandbox
grep "V2_protein.faa.gz" md5checksums.txt
d593406dc180606713164a17c1a05d0a  ./GCF_016801865.2_TS_CPP_V2_protein.faa.gz

Now, compute the checksum for your copy of the file:

md5sum GCF_016801865.2_TS_CPP_V2_protein.faa.gz
d593406dc180606713164a17c1a05d0a  GCF_016801865.2_TS_CPP_V2_protein.faa.gz

The two are identical, so your download is intact. Rather than comparing checksums by eye, you can let md5sum do the comparison with its -c (check) option. This option takes lines in the format above (from a file or from standard in), computes the checksum for each listed file, and compares it to the listed one:

grep "V2_protein.faa.gz" md5checksums.txt | md5sum -c
./GCF_016801865.2_TS_CPP_V2_protein.faa.gz: OK
  • We only passed the line for the protein file, because md5checksums.txt lists ~190 files and we only have a few of them. When a sequencing facility sends you a checksum file for exactly your FASTQ files, you can simply run md5sum -c md5.txt.
  • Run the check from inside the dir with the files, because the file names in a checksum file are usually relative paths (here, ./<file-name>).

If a file doesn’t match, md5sum clearly says so, and you should download or transfer that file again:

./GCF_016801865.2_TS_CPP_V2_protein.faa.gz: FAILED
md5sum: WARNING: 1 computed checksum did NOT match

When you’re done, move back to your personal dir:

cd ../..
NoteSHA checksums (Click to expand)

MD5 is still very common for checking data integrity, since it reliably catches accidental corruption. However, it is no longer considered secure against deliberate tampering. Newer tools and software distributions therefore often provide SHA-256 checksums instead, which work the same way, with the sha256sum command (e.g. sha256sum -c sha256sums.txt).

5 File permissions

5.1 Introduction to file permissions

File “permissions” are what different categories of users are permitted to do with files and dirs. Being able to view and modify file permissions is useful when you:

  • Get a “Permission denied” error and want to understand why
  • Want to make your data read-only to prevent accidental modification or deletion
  • Need to share files with other users at OSC

There are three different permissions that can be independently controlled, and their meaning differs between files and dirs:

Permission For a file For a dir
Read (r) View and copy its contents List the names of the files in it
Write (w) Modify or overwrite its contents Add, remove, or rename files in it
Execute (x) Run it as a program (see the box below) Enter it (cd) and access the files in it

You can think of a dir as a room with a list of its contents on the door: r lets you read the list, x lets you walk in, and w lets you put things in or take them out. Two consequences of this often surprise people:

  • Whether you can remove or rename a file depends on the permissions of its dir: a file’s own write permissions only control whether its contents can be changed.
  • To access a file, you need execute permissions for its dir — and for every dir along the path to it.

While it is possible to set permissions for individual users, they are most easily and commonly set for three different user categories:

  • Owner (or “user”) (u) — By default, this is the person who created the file or dir. This includes cases where this person merely copied or downloaded files: e.g., after you have copied someone else’s FASTQ files, you are the owner of these copies.
  • Group (g) — At OSC, groups correspond to OSC projects, like PAS3493. By default, a new file’s group is your own default project, even when you create the file in another project’s dir.
  • Other (o) — Any other user.

You can also refer to all three of these categories at once with a (all).

NoteExecuting a file? (Click to expand)

Executing a file means running it as a program/command. For example, when we run the FastQC program with the command fastqc, we are really executing a binary (executable) file somewhere on the system. Similarly, self-written shell scripts can be executed if they have execute permissions set.

In this course, we have been running shell scripts like so:

bash scripts/fastqc.sh

Here, the program that is being executed is bash, which then reads and runs the script. The script itself therefore doesn’t need execute permissions. If you give it execute permissions (e.g. with chmod u+x scripts/fastqc.sh, see below), you can also run the script directly, by typing its path — the shell then uses the script’s shebang line (#!/bin/bash) to determine which program should run it:

scripts/fastqc.sh

For a script in your current working dir, you need to precede its name with ./ (e.g., ./fastqc.sh), since just typing fastqc.sh would make the shell look for a command with that name.

5.2 Viewing file permissions

To show file permissions, use ls with the -l (long format) option that we’ve seen before, which should show you something like this:

ls -lh garrigos
total 2.5K
drwxrwx---+ 2 jelmer PAS0471 4.0K Sep  9 13:46 fastq
drwxrwx---+ 2 jelmer PAS0471 4.0K Sep  9 13:46 meta
-rw-rw----+ 1 jelmer PAS0471 2.3K Sep  9 13:46 README.md
drwxrwx---+ 2 jelmer PAS0471 4.0K Sep  9 13:46 ref
drwxrwx---+ 2 jelmer PAS0471 4.0K Sep 16 13:26 sandbox

With annotations:

Here is an overview of the file permission notation in ls -l output:

For example:

  • rwxrwxr-x means: read, write, and execute permissions are set for the owner (first rwx) and the group (second rwx), and read and execute but not write permissions for others (r-x at the end).

  • rw-rw-r-- means: read and write but not execute permissions are set for both the owner (first rw-) and the group (second rw-), and only read permissions for others (r-- at the end).

5.3 Default permissions at OSC

Most commonly, files and dirs that you create at OSC will by default have:

  • Read permissions for owner (you) and group
  • Write permissions only for owner (you)

More generally, by default:

  • OSC users that are not members of a specific project can’t access that project’s files in /fs/ess/ and /fs/scratch at all.
  • Other OSC users cannot access your personal Home dir files — so it’s never a good idea to keep files there that should be accessible to collaborators.

Finally, other members of PAS3493 can always read files created in the project dir, but they can only edit them if the file’s group is PAS3493.

Here, the ls -l output can be misleading. For example, my files on this page show rw-rw----, but their group is PAS0471 (my own default group), so those group permissions apply to members of PAS0471, not PAS3493. PAS3493 members get read access through an “access control list” (ACL), an extra layer of permissions that is indicated by the + at the end of the permission string. To see a file’s ACL, use getfacl <file>: for one of my files, it includes the line group:PAS3493:r-x #effective:r--, meaning that PAS3493 members can only read it.

5.4 Changing file permissions

Let’s create a file to play around with file permissions:

# Create a test file
mkdir -p sandbox
cd sandbox
touch testfile.txt

# Check the default permissions
ls -l testfile.txt
-rw-rw----+ 1 jelmer PAS0471 0 Mar  7 13:36 testfile.txt

To change a file’s permissions, you can use the chmod command. There are two main ways to use this command, one of which uses symbols as follows:

  • + : add a permission
  • - : remove a permission
  • = : set permissions to exactly this

These are used with both the kind of permission (r / w / x) and the user category (a / u / g / o). For example, a+r means that for all, you add (+) read permissions. Let’s see some commands:

  • To add read (r) permissions for all (a):

    chmod a+r testfile.txt

ls -l testfile.txt
    -rw-rw-r--+ 1 jelmer PAS0471 0 Mar  7 13:36 testfile.txt

  • To set read + write + execute (rwx) permissions for all (a):

    chmod a=rwx testfile.txt

ls -l testfile.txt
    -rwxrwxrwx+ 1 jelmer PAS0471 0 Mar  7 13:36 testfile.txt

    Because the file is now “executable”, its name should display in green in your terminal.

  • To remove write (w) permissions for others (o):

    # chmod <who>-<permission-to-remove>:
chmod o-w testfile.txt

ls -l testfile.txt
    -rwxrwxr-x+ 1 jelmer PAS0471 0 Mar  7 13:36 testfile.txt
NoteAn alternative method: changing file permissions with numbers (Click to expand)

chmod alternatively accepts a series of 3 numbers (for user, group, and others, respectively) to set permissions, where each permission is “worth” the following number of points:

Nr Permission
0 none
1 x
2 w
4 r
Nr Permission
3 w + x
5 r + x
6 r + w
7 r + w + x

For example, to set read + write permissions for yourself, only read permissions for the group, and no permissions for others:

chmod 640 testfile.txt

To set read + write + execute permissions for yourself, and only read permission for the group and others:

chmod 744 testfile.txt

5.5 Changing permissions for directories

chmod is not recursive by default: you need the -R option to change permissions throughout a dir hierarchy. For example:

chmod -R g+r my-dir

Recall that to access anything inside a dir, you need execute permissions for it, which is something to keep in mind when you want to give others access to your files.

For example, if the group doesn’t already have execute permissions for my-dir, the g+r command above would let group members list the names of files in my-dir, but not open them. To also set execute permissions throughout a dir hierarchy, but only for dirs (and files that already have execute permissions for someone), use an X (uppercase x):

chmod -R g+rX my-dir

5.6 Making your data read-only

Now, let’s see how you can make your data read-only. Here, we’ll work with the files in the garrigos/fastq/ dir, so let’s check the initial permissions first:

cd ..
ls -l garrigos/fastq/ | head -n 3
total 963552
-rw-rw----+ 1 jelmer PAS0471 21266097 Sep  9 13:46 S63_R1.fastq.gz
-rw-rw----+ 1 jelmer PAS0471 22700521 Sep  9 13:46 S63_R2.fastq.gz

To make this data read-only, remove write permissions for both the files and the dir that contains them, which the -R option does in one go:

chmod -R a-w garrigos/fastq

After running this command, let’s check the permissions again:

ls -l garrigos/fastq/ | head -n 3
total 963552
-r--r-----+ 1 jelmer PAS0471 21266097 Sep  9 13:46 S63_R1.fastq.gz
-r--r-----+ 1 jelmer PAS0471 22700521 Sep  9 13:46 S63_R2.fastq.gz

This protects your data in two ways:

  • Without write permissions for the files, they can’t be modified (e.g., accidentally overwritten with >).
  • Without write permissions for the dir, files in it can’t be removed or renamed. For example, rm (even rm -f) will now fail with a “Permission denied” error for any file in garrigos/fastq.

For example, try to create a new file in the dir:

touch garrigos/fastq/test.txt
touch: cannot touch 'garrigos/fastq/test.txt': Permission denied

If you later do need to add or remove files, temporarily give yourself write permissions for the dir again:

chmod u+w garrigos/fastq
# [Add or remove files]
chmod u-w garrigos/fastq
NoteWhy protecting only the files isn’t enough (Click to expand)

As mentioned above, removing a file is controlled by the permissions of its dir. If only a file itself is write-protected, rm merely asks for confirmation:

rm read-only.txt
rm: remove write-protected regular file ‘read-only.txt’?

Answering y (yes) removes the file, and the -f (force) option of rm skips such prompts altogether.

You’ll likely run into these prompts when removing a dir with a Git repo, since Git makes the files in its .git/objects dir read-only. Using rm -rf avoids having to confirm the removal of each of those files, but be careful with the -f option, since it removes files without asking.

6 More about file compression

This section builds on the w11a section on file compression, which covers the basics of gzip and gunzip.

6.1 Compressing program output

Often, a program will output unzipped data to standard out, which we can immediately pipe to gzip, so that we never write the large uncompressed file to disk, saving both disk space and time:

trimmer in.fastq.gz | gzip > out.fastq.gz

(Note that because the input to gzip comes from standard in, the output will by default be to standard out!)

NoteConcatenating compressed data (Click to expand)

Concatenating files means you combine them into a single file, simply printing them back-to-back. When it is okay to concatenate files2, this can be done very easily.

To add a second FASTQ file to an existing gzipped file, we can simply use >>:

ls
in.fastq.gz in2.fastq
gzip -c in2.fastq >> in.fastq.gz

Even more conveniently, if we have two gzipped FASTQ files for the same sample but from different Illumina lanes:

cat smpA_L001_R1.fastq.gz smpA_L002_R1.fastq.gz > smpA_R1.fastq.gz

6.2 Archives with tar

Software, databases, and sometimes data sets are often distributed as a single .tar.gz (or .tgz) file, a so-called “tarball”. This is an “archive” file that contains multiple files and dirs, which were combined into a single file with the tar command and then gzip-compressed. Since gzip itself can only compress individual files, tar is also what you would use to pack up a dir, e.g. to share it or to back it up.

# Create (-c) a gzip-compressed (-z) archive file (-f) from the dir 'results':
tar -czvf results.tar.gz results/

# List (-t) the contents of an archive without extracting it:
tar -tzvf results.tar.gz

# Extract (-x) the contents of an archive into your working dir:
tar -xzvf results.tar.gz
  • The -v (verbose) option makes tar print the names of the files it processes.
  • The -f option should come last, because it must be directly followed by the name of the archive file.
  • When extracting, tar recreates the dirs stored in the archive, and overwrites existing files with the same names without asking — so when in doubt, list the contents first.

Exercise: Compression

You have a dir with three FASTQ files: A.fastq, B.fastq, and C.fastq. Predict which files you would end up with after running each of the following commands (each starting from the same three files):

  1. gzip *.fastq

      Click to see the solution

    A.fastq.gz, B.fastq.gz, and C.fastq.gz: gzip compresses each file separately, and removes the originals.

  2. gzip -c *.fastq > all.fastq.gz

      Click to see the solution

    The three original files, plus all.fastq.gz, which contains the reads of all three files back-to-back (see the box on concatenating compressed data above) — so you can no longer tell which reads came from which file!

  3. tar -czf all.tar.gz *.fastq

      Click to see the solution

    The three original files, plus all.tar.gz, from which you can extract the three separate files again.
