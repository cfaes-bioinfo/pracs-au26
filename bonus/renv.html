1 Introduction

1.1 Overview

In w14a, you saw how sessionInfo() records which versions of R and R packages you used. That is useful information, but it doesn’t help you or anyone else get those versions back.

So far, you have installed all R packages in a single personal library: a folder in your Home directory that is shared by all your R projects. This works fine most of the time, but has some downsides:

  • When you update a package for one project, it is updated for all your projects, and code in another project may stop working.
  • If someone else (or you, on another computer or a year from now) wants to rerun your code, they will install the latest versions of all packages, which may give different results or errors.

renv solves these problems by giving each project its own package library, and by recording the exact package versions in a file that you commit to Git. It is the R counterpart of the Conda environments and containers that you have used for command-line software (see w6b and the Conda bonus page).

1.2 Learning goals

On this page, you will learn:

  • How renv works: project libraries, the lockfile, and the package cache
  • How to set up renv in a project
  • How to record and restore package versions
  • Which renv files to commit to Git
  • How to use renv with Quarto, Rscript, and Slurm batch jobs

2 How renv works

renv adds three things to a project:

  • A project library (renv/library/): a folder with the R packages for this project only.
  • A lockfile (renv.lock): a text file that lists the R version and the exact version and source (e.g. CRAN or Bioconductor) of each package.
  • An .Rprofile file: R runs the code in this file whenever it starts in this folder, and renv uses it to switch R to the project library. You’ll learn more about what this means for running your code below.

Installing the same packages again for each project would be slow and take a lot of disk space. Instead, renv keeps a package cache in your Home directory, installs each package version only once, and adds links to the cache in each project library.

3 Setting up renv in a project

3.1 Setting up a practice project

We’ll first practice with renv in a new folder, before you (optionally) use it in your Final Project.

  1. In the terminal, create a folder renv-practice in your personal dir:

    mkdir /fs/ess/PAS3493/people/$USER/renv-practice

  2. Open this folder in Positron (File > Open Folder). You need to do this, because renv only works when R starts in the project’s top-level folder.

  3. Create a Quarto document analysis.qmd with a code chunk that loads two packages:

    library(ggplot2)
library(dplyr)

3.2 Initializing renv

To set up renv in your project, run in the R console:

renv::init()

renv::init() does the following:

  • It scans your code for the packages you use, such as those loaded with library().
  • It adds these packages, and the packages they depend on, to the project library. Packages that are already installed in your personal library are linked rather than downloaded again, so this should be fairly quick.
  • It writes the lockfile, creates the .Rprofile file, and restarts R so that R uses the project library.

Take a look at the files that were created:

ls -a

Besides analysis.qmd, you should see .Rprofile, renv.lock, and renv/. renv.lock is a text file in JSON format — open it to see what it records.

TipIs renv active?

When R starts in a renv project, it prints a message like - Project '/fs/ess/...' loaded. [renv 1.3.1]. You can also run .libPaths(): when renv is active, the first folder is inside the project’s renv folder.

4 Recording and restoring package versions

4.1 Installing packages and taking a snapshot

In a renv project, you install packages as usual, with install.packages() or renv::install(), but they go into the project library. Install the janitor package, and add library(janitor) to your Quarto document:

install.packages("janitor")

Installing a package does not update the lockfile. To see the difference between your project library and the lockfile, run:

renv::status()

This should report that janitor is used and installed, but not recorded in the lockfile. To update the lockfile, take a snapshot:

renv::snapshot()
What would happen if you took a snapshot after installing janitor, but without adding library(janitor) to your code?

By default, renv::snapshot() only records packages that your code uses (and the packages they depend on). So, janitor would not be recorded in the lockfile. That’s usually what you want: a package that you tried out but don’t use doesn’t need to be installed by anyone who reruns your code.

A good routine is to run renv::status() and renv::snapshot() whenever you have started using a new package, and before you commit your code.

4.2 Updating packages and going back

To update the packages in your project library, use:

renv::update()

If everything still works, take a snapshot to record the new versions. If something broke, you can go back to the versions in the lockfile:

renv::restore()

4.3 Bioconductor packages

renv can also install Bioconductor packages, using a bioc:: prefix:

renv::install("bioc::DESeq2")

The lockfile then also records the Bioconductor version. (Packages installed with BiocManager::install() are recorded too.)

5 renv and Git

Commit these renv files to your Git repository:

  • renv.lock
  • .Rprofile
  • renv/activate.R
  • renv/settings.json

Don’t commit the project library itself. You don’t need to add anything to your .gitignore for this: renv creates a renv/.gitignore file that excludes the library and other local files.

When you take a new snapshot, commit the updated renv.lock along with the code that uses the new packages. This way, your Git history records which package versions belonged to which version of your code.

5.1 Rerunning someone else’s renv project

To rerun a project that uses renv, for example one that you cloned from GitHub:

  1. Open the project’s folder in Positron. When R starts, renv installs itself if needed.

  2. Install the packages from the lockfile:

    renv::restore()

renv records the R version in the lockfile, but it doesn’t install R itself. If your R version is different, renv prints a warning. At OSC, you can see the available R versions with module spider R, and it’s a good idea to mention the R module you used in your project’s README.

6 Running code in a renv project

renv is only active when R starts in the project’s top-level folder, because that’s where the .Rprofile file is. Otherwise, R silently uses your personal library instead, so your code may still run, but with different package versions. Here’s what that means in practice:

  • In Positron, open the project’s top-level folder, not a folder above it like your personal dir.

  • In the terminal, run quarto render and Rscript from the project’s top-level folder, also when the file you’re running is in a subfolder:

    quarto render scripts/analysis.qmd

  • In Slurm batch jobs, a job starts in the folder that you submitted it from, so submit from the project’s top-level folder. The render.sh script from the R bonus page then works without changes:

    sbatch scripts/render.sh scripts/analysis.qmd

7 Using renv in your Final Project

Using renv in your Final Project is optional — as the rubric says, R packages can simply be installed as we did in class. If you want to use renv:

  1. Open your FP folder in Positron.
  2. Run renv::init(), check the lockfile, and commit the renv files.
  3. In your README, mention that the project uses renv, and that renv::restore() installs the packages.
