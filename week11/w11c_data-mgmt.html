Why you should prefer relative paths

Absolute paths: a disadvantage?

Absolute paths don’t depend on your working dir — so what could be a disadvantage of using them?

Absolute vs. relative paths

Absolute and relative paths to a FASTQ file in two project dirs.
The relative paths start from the project’s top-level dir (~ is your Home dir).

Moving project dirs

After moving both projects into OneDrive, the absolute path has changed, but the relative path has not.

Relative paths keep working after moving project dirs — as long as you always use the project’s top-level dir as your working dir.

Raw data management

Raw data is precious

Your raw data (for omics, usually FASTQ files) are the results of your experiment, and often expensive and labor-intensive to produce.

Never delete it

  • It remains your ground truth, even after you’ve produced processed files.

  • It allows you and others to reproduce your results, and to re-analyze the data with new methods.

Keep multiple copies

  • Ideally in at least two different physical locations.

  • At OSC, never store it only in a scratch dir, where unused files are automatically deleted.

Share it publicly

  • After publication.

  • Required by most journals and funding agencies, and long expected for sequencing data.

Documenting and protecting raw data

Document it

  • Keep track of data provenance: when and from where did you get the data?

  • Keep track of the metadata for each sample.

  • Use standard, preferably plain-text file formats.

Protect it

  • Consider making it read-only with file permissions (bonus material).

  • After downloading or sharing key data, consider using “checksums” to check that files were transferred entirely (bonus material).

Metadata in spreadsheets

Spreadsheet recommendations

Entering sample metadata in Excel is fine, as long as code can read the spreadsheet without manual cleanup. Some recommendations from The Turing Way’s Data Organisation in Spreadsheets:

Structure

  • One row per sample, one column per variable, and a single header row.
  • Only one value per cell.
  • No merged cells, colors, or formatting to store information (add a column instead).
  • No calculations in the raw metadata spreadsheet.
  • Export the final version as a CSV or TSV file.

Content

  • Consistent sample names, category labels, and units.
  • No spaces or special characters in sample and column names (time_point, not Time point (days)).
  • Dates as YYYY-MM-DD (e.g. 2026-11-04): unambiguous and sorts correctly.
  • A single code for missing data (e.g. NA), rather than some empty cells.

Spreadsheet example and pitfall

Example

The garrigos/meta/metadata.tsv file you’ve seen before:

sample_id       time    treatment
S82     10dpi   cathemerium
S75     10dpi   cathemerium
S78     10dpi   control
S84     10dpi   control
S76     10dpi   relictum

In week 13, you’ll see that this layout is called “tidy data”, which R works with very well.

Excel turns gene names into dates

  • Excel converts text that looks like a date: SEPT2 and MARCH1 become 2-Sep and 1-Mar.

  • About 20% of papers with gene lists in Excel files contained such errors, and several human genes were renamed because of it (SEPT2 is now SEPTIN2).

To prevent this, set such columns to the “Text” format before entering or pasting data.

Sharing data

Sharing is required

Public access

By the end of 2025, all federally-funded research must make articles and data publicly available immediately upon journal publication with no waiting periods allowed.

— Federal Research Policy Guide from OSU’s ERIK

Data Management Plans

DMPs specify how you’ll manage and share your data, and major funders require them (NSF since 2011):

A DMP is currently required for all competitive grant programs of the United States Department of Agriculture and the National Science Foundation.

— Grünwald et al. (2024)

See the guidelines for USDA NIFA and NSF grants.

Platforms for sharing data

NCBI

  • Raw reads go to the SRA (or Europe’s ENA).

  • Also for genome assemblies and annotations.

  • Count tables go to GEO, which also uploads the reads to the SRA.

General repositories

  • For other results and data.

  • E.g. Dryad and Zenodo.

  • Increasingly required by journals.

Code

  • GitHub (or GitLab, Bitbucket), ideally with a DOI via Zenodo (next slide).

  • Some journals also require code in a general repository, where it may get a manual quality check.

OSU’s Research Commons has data sharing guides and offers consultations.

A DOI for your GitHub repo with Zenodo

Why?

  • A GitHub repo can be changed or deleted at any time: a poor permanent reference in a paper.

  • Zenodo, a general repository run by CERN, can archive a snapshot of your repo and give it a citable DOI.

How?

  1. Log in to Zenodo with your GitHub account.
  2. In Zenodo’s GitHub settings, flip the switch next to your (public) repo.
  3. On GitHub, create a “release” of your repo (“Create a new release” in the repo’s right sidebar).

Zenodo then archives the release and assigns it a DOI. Each release gets its own DOI, plus a “concept DOI” always points to the latest version (more info).

Syncing OSC and local files

Should I keep my OSC and local dirs synced?

Syncing strategy

Fully automatic syncing like with OneDrive or Dropbox isn’t possible — and with large OSC data, you may not want it. Instead:

  • Sync version-controlled files (code, etc.) via Git/GitHub.
  • Periodically sync other files with the transfer methods discussed next.

Or: work in one place

  • Running analyses both at OSC and locally makes syncing a hassle.

  • So for projects that need OSC, try to do all your analyses there.

  • Your local computer (and/or OneDrive/Teams) can then hold an entirely separate set of files, like the manuscript.
