2 Compute jobs overview

Automated scheduling software allows hundreds of people with different requirements to effectively and fairly access compute nodes at supercomputers. OSC uses Slurm (Simple Linux Utility for Resource Management) for this.

As you’ve learned, a reservation of resources on compute nodes is called a compute job. Here are the main ways to start a compute job at OSC:

  1. “Interactive Apps” — Run programs with GUIs (e.g. VS Code or RStudio) in your browser through OnDemand.
  2. Interactive shell jobs — Start an interactive shell on a compute node.
  3. Batch (non-interactive) jobs — Run a script on a compute node “remotely”: without going to that node yourself.

We’ve already worked a lot with the VS Code Interactive App, and interactive shell jobs are covered in this week’s optional self-study material (you should rarely need these). What we’ll focus on in this session are batch jobs.

3 Basics of Slurm batch jobs

When you submit a batch job, you ask the Slurm scheduler to run a script “out of sight” on a compute node. While that script runs on a compute node, you will stay in your current shell at your current node. After you submit a batch job, it will continue to run even if you log off from OSC and shut down your computer.

3.1 The sbatch command

You can use Slurm’s sbatch command to submit a batch job. But first, let’s recall how we’ve run shell scripts so far:

bash scripts/printname.sh Jane Doe
First name: Jane, last name: Doe

The above command ran the script on whatever node you are on, and printed output to the screen. To instead submit the script to the Slurm queue, start by simply replacing bash with sbatch:

sbatch scripts/printname.sh Jane Doe
sbatch: error: ERROR: Job invalid: Must specify account for job
sbatch: error: Batch job submission failed: Unspecified error

However, as the error message above (“Must specify account for job”) informs us, you need to indicate which OSC Project (or as Slurm puts it, “account”) you want to use for this compute job. Use the --account= option to do this:

sbatch --account=PAS3493 scripts/printname.sh Jane Doe
Submitted batch job 56603792

  • This output line means your job was successfully submitted (no further job output will be printed to your screen).

  • The number in this output is the job ID: a unique identifier among all compute jobs by all users at OSC, which you can use to monitor and manage the job. Each of us will therefore see a different job ID pop up.

  • After submitting a batch job, you immediately get your prompt back. The job will run outside of your view, and you can continue doing other things in the shell while it does, or even log off. This behavior allows you to submit many jobs at the same time: you don’t have to wait for other jobs to finish, or even to start!

  • Note the new option style in --account=PAS3493: the option and its value are separated by an = rather than a space. Many commands accept this style for long options (those starting with --), and it’s the usual style for sbatch options.

sbatch options and script arguments

As was implicit in the command above, we can use sbatch options and script arguments in one command like so:

sbatch [sbatch-options] myscript.sh [script-arguments]

Depending on the details of the script itself, any combination of sbatch options and script arguments is possible:

# No options/arguments for either:
sbatch scripts/printname.sh

# Script arguments but no sbatch option:
sbatch scripts/printname.sh Jane Doe

# sbatch option but no script arguments:
sbatch --account=PAS3493 scripts/printname.sh

# Both sbatch option and script arguments:
sbatch --account=PAS3493 scripts/printname.sh Jane Doe

If the account had been specified in some other way, the job would have run and printed the output in option C.

3.2 Where does the script’s output go?

Slurm log files

Above, we saw that when you ran printname.sh “directly” with bash, the script’s output was printed to the screen, whereas when you submitted it as a batch job, only Submitted batch job <job-id> was printed to screen. In the latter case, where did this output go?

It ended up in a file called slurm-<job-id>.out (e.g., slurm-56603792.out; since each job ID is unique to a given job, each file has a different number). We’ll call this type of file a Slurm log file.

Getting this output in log files instead of printed to screen may seem inconvenient. Can you think of any reasons why we may not want batch job output printed to screen, even if it were possible?

There are several reasons, such as:

  • If you log off after submitting a batch job, any output printed to screen would be lost.
  • The power of submitting batch jobs is that you can submit many at once — e.g. one per sample, running the same script. If the output from all those scripts ends up on your screen, things become a big mess, and you have no lasting record of what happened.

If you run ls, you should see a Slurm log file for the job you just submitted:

ls
scripts slurm-56603792.out

Let’s take a look at its contents:

# Auto-complete the file name with Tab: you'll have a different job ID!
cat slurm-56603792.out
First name: Jane, last name: Doe

This file contains what the script printed to screen when we ran it with bash — nothing more or less. That includes any error messages: recall from week 4 that besides regular output (“standard output”), commands can also print error messages (“standard error”) to the screen. In a batch job, both end up in the Slurm log file1.

TipThe working directory stays the same

When the scripts in batch jobs are being run, they start in the directory that they were submitted from: that is, the working directory remains the same, and you shouldn’t have to make special adjustments to paths. Additionally, as you’ve seen, Slurm log files will (by default) be created in the dir you submitted the job from.

Cleaning up the Slurm logs

When submitting batch jobs, your working dir can easily become a confusing mess of anonymous-looking Slurm log files. These two strategies help to prevent this:

  • Changing the Slurm log file name to include a one- or two-word description of the job/script (next lecture).
  • Cleaning up your Slurm log files, by:
    • Removing them when no longer needed — as is e.g. appropriate for our current Slurm log file.
    • Moving them to the same location as other outputs by that script. This is often appropriate after you’ve run a bioinformatics tool, since the Slurm log file may contain some info you’d like to keep. (For example, you can move Slurm log files for jobs that ran FastQC, and produced outputs in results/fastqc, to a dir results/fastqc/logs.)

In this case, we’ll simply remove the Slurm log file, because it has no information that we need to keep:

# Again, auto-complete the file name to include the correct job ID
rm slurm-56603792.out

3.3 Adding sbatch options in scripts

The --account= option is just one of many options you can use when submitting a job, but is the only required one. For all other options, defaults are set, such as the amount of time (1 hour) and the number of cores (1 core).

Instead of adding these options after the sbatch command when submitting the script, you can also add them inside the script. This is a useful alternative because:

  • You’ll often want to specify several options, which could otherwise lead to very long sbatch commands.
  • It allows you to store a script’s typical Slurm options as part of the script, so you don’t have to remember them.

These options are added in the script using another type of special comment line (akin to the shebang #!/bin/bash line) that is marked by #SBATCH.

WarningMake sure the #SBATCH lines are at the top of the script (Click to expand)

Just like the shebang line, #SBATCH lines must be located at the top of the script: Slurm stops looking for them as soon as it reaches the first line with a command (comment lines and blank lines before that are fine). Any #SBATCH lines further down are silently ignored: you won’t get an error, but those options won’t be applied either.

Another pitfall is a line that doesn’t start with exactly #SBATCH, like # SBATCH (with a space) or #sbatch — these will similarly be silently ignored.

Let’s add an #SBATCH line to the printname.sh script, such that the first few lines read:

scripts/printname.sh (excerpt)
#!/bin/bash
#SBATCH --account=PAS3493
set -euo pipefail

So, the equivalent of adding --account=PAS3493 after sbatch on the command line is a line in your script that reads #SBATCH --account=PAS3493. Now, you can run the sbatch command without options (which failed earlier):

sbatch scripts/printname.sh Jane Doe
Submitted batch job 56603905
Notesbatch option precedence!

If you specify the same sbatch option both on the command line and in the script, the command line option takes precedence, so the one in the script is ignored. This is sensible because it allows you to provide “defaults” inside the script, and change one or more of those when needed “on the go” on the command line.

TipRunning a script with #SBATCH lines in other contexts and on other computers (Click to expand)

Because #SBATCH lines are special comment lines, they will simply be ignored (and not throw any errors) when you run a script with them in other contexts. For example, when you’re running the script with bash instead of sbatch at OSC, or when running it on a computer without Slurm installed. This is convenient and means that these lines do not reduce the portability of your scripts.

4 Monitoring batch jobs

Real batch jobs for your research projects may run for a while. You may also be submitting many jobs at once. Finally, longer-running jobs and those that ask for many cores sometimes remain queued for a while before they start. For these reasons, it’s important to know how you can monitor your batch jobs.

4.1 Checking a job’s status

Batch job behavior

After you submit a job, it may initially be waiting to get resources allocated to it: in other words, the job may be pending. Eventually, and often very quickly, the job will start running. You’ve seen this process with the VS Code Interactive App job as well.

Whereas Interactive App jobs will keep running until they’ve reached the end of the allocated time2, batch jobs will stop as soon as the script has finished. And if the script is still running when the job runs out of its allocated time, it will be killed (stopped) right away.

The squeue command

You can check the status of your batch jobs using the below squeue Slurm command, where:

  • You specify your username with the -u option (without this, you’d see everyone’s jobs!). In this example, I used the environment variable $USER to get your user name, but you can simply type your username if that’s easier.
  • The option -l (lowercase L, “long”) will produce the more verbose output shown. Without it, the output will be a bit more cryptic, with abbreviations.
# Or: squeue -u jelmer -l
squeue -u $USER -l
Mon Oct 26 14:21:34 2026
        JOBID PARTITION     NAME     USER    STATE       TIME TIME_LIMI  NODES NODELIST(REASON)
     56603512 condo-osu ondemand   jelmer  RUNNING      36:34   2:00:00      1 p0133

The output always starts with a line with the date & time and a header line with all-caps column names. Then, if there are any jobs in the queue, there will be one line per job. In this case there is only one job in the queue, which is the VS Code Interactive App job.

Across the output columns, the following pieces of information about each job are listed:

Column Explanation
JOBID The job ID
PARTITION The type of queue (usually auto-assigned and not of interest)
NAME The name of the job (by default the name of the script when submitting a script)
USER The username of the person who submitted the job
STATE The job’s state, usually either PENDING or RUNNING (Finished jobs do not appear)
TIME For how long the job has been running (here in “minutes:seconds” format)
TIME_LIMIT The amount of time you reserved for the job (here in “hours:minutes:seconds” format)
NODES The number of nodes reserved for the job
NODELIST(REASON) – When running: the ID of the node on which it is running.
– When pending: why the job is pending

4.2 A sleepy script for practice

We’ll use another short shell script to practice monitoring and managing batch jobs. First create a new file:

touch scripts/sleep.sh

Open the file in the VS Code editor and paste the following into it:

scripts/sleep.sh
#!/bin/bash
#SBATCH --account=PAS3493
set -euo pipefail

echo "I will sleep for 30 seconds" > sleep.txt

sleep 30s

echo "I'm awake! Successfully finished script sleep.sh"

First, run the script directly with bash, and notice that you won’t get your prompt back until the script finishes, 30 seconds later:

bash scripts/sleep.sh
I'm awake! Successfully finished script sleep.sh

The other line of text was redirected to sleep.txt:

cat sleep.txt
I will sleep for 30 seconds

Remove the output file before we try this as a batch job:

rm sleep.txt

4.3 Checking a job’s output files

Two types of output

As you saw in Exercise 2, a batch job can produce output in two places. These correspond to an important distinction between two general types of output that scripts, commands, and programs can have:

  1. Output that is printed to screen, both standard output and standard error.
    • Most shell commands, like echo in sleep.sh, by default print their output to the screen.
    • Other programs, like you’ve seen with FastQC, only print “logging”-type output (e.g. progress and error messages) to the screen3.
  2. Output that is written to files.
    • Programs like FastQC write their main results to files.
    • Shell commands write to files when you redirect their output, like the first echo command in sleep.sh.

Here is what happens to each of these when you submit a script as a batch job instead of running it directly with bash:

Type of output Run with bash Submit with sbatch
Printed to screen (stdout/stderr) Printed to the screen Written to the Slurm log file
Written to files Written to those files Written to the exact same files

In other words, submitting a script as a batch job only changes where “screen output” goes, and not what happens to any output files.

Even if you’ve been monitoring a job with squeue, you should always check both types of output to make sure it ran successfully: the Slurm log file and any output files created by the script.

Let’s keep things tidy and remove the script’s outputs:

rm slurm* sleep.txt
WarningBe careful with deleting Slurm log files

If you delete a Slurm log file for a job that is still running, the file will not be recreated when the job produces more logging output later on. That means that if you accidentally do this and the logging output is of key importance to interpreting other outputs, or making sure it ran successfully, you are better off canceling the job entirely and trying again. 😕

4.4 Canceling jobs

Sometimes, you want to cancel one or more jobs. For example, you may realize you made a mistake in the script or used the wrong input files as arguments. You can cancel jobs that are either pending or running using scancel:

# Cancel a specific job:
scancel 56604061

# Cancel all your running and queued jobs (careful with this!
# This also cancels your VS Code session, since that is a compute job too):
scancel -u $USER
Say you’ve submitted a job, and while it’s still pending, you notice and fix a mistake in the script. Will the job run the fixed script once it starts?

No: when you submit a job, Slurm stores a copy of the script, and that copy is what the job will run. So, after fixing a script, cancel any pending or running jobs that use it, and submit them again.

(But input files are only read when the job runs, so changing those does affect pending jobs.)

NoteThe “Jobs” menu in OnDemand (added 10/29) (Click to expand)

The OnDemand website has a “Jobs” dropdown menu in its top bar, with the following items:

  • Active Jobs — A web-based alternative to squeue that lists your queued and running jobs. By default, only your own jobs are shown (you can switch the filter at the top from “Your Jobs” to “All Jobs”). Click the arrow next to a job to see more details, such as the node(s) it’s running on, the number of cores, and the time limit. You can also cancel a job with the trash can icon (like scancel), and open the job’s working directory in the File Manager or a terminal.
  • Job Composer — A tool to write and submit batch jobs using templates and web forms. We won’t use this, because we write our own scripts and submit them with sbatch in the terminal.
  • Project Manager — A newer replacement for the Job Composer, in which you organize your work into “projects” (directories) and submit jobs from them using forms. We won’t use this either, for the same reason.
