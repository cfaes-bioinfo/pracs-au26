2 Common Slurm/sbatch options

In class, we’ll go through the most commonly used sbatch options using the slides below (open them in a separate tab for a full-screen view).

After that, there’s a self-study exercise on what happens when a job exceeds its time limit. This section also has a reference table of these and some additional options, and a few more notes on cores, memory, and Slurm log files.

Here are the main options from the slides:

And some additional ones:

NoteWhat about nodes and tasks? (Click to expand)

You may wonder why the option is --cpus-per-task rather than just --cpus. Slurm can also reserve multiple nodes (--nodes) and multiple tasks, i.e. independent processes (--ntasks). Both default to 1, which is almost always what you want in bioinformatics: for example, multiple nodes are only useful for programs parallelized with “MPI”, which is rare. With 1 node and 1 task, --cpus-per-task simply sets the number of cores.

You may also see --ntasks=n being used for multi-threading, including in OSC’s documentation: in practice, that also gives you n cores that a program can use. (Yes, this is confusing!)

WarningIt is not always clear what happened when your job ran out of memory (Click to expand)

Whereas you get a very clear Slurm error message when you hit the time limit (as seen in the self-study exercise above), hitting the memory limit can result in a variety of errors.

But look for keywords such as “Killed”, “Out of Memory” / “OOM”, and “Core Dumped”, as well as actual “dumped cores” in your working dir (large files with names like core.<number>, which can be deleted).

If you see these or otherwise suspect that your job ran out of memory, resubmit it with an increased requested amount of memory. To check, you can also use seff to see a finished job’s peak memory use, or sacct, which lists jobs that ran out of memory as OUT_OF_MEMORY (see the optional self-study page).

Self-study exercise: Exceed the time limit

  1. Modify your scripts/sleep.sh script from the previous lecture so that it reserves only 1 minute (#SBATCH --time=1), but sleeps for 100 seconds (sleep 100s). Then, submit it, and once it no longer shows up in squeue, check which output files were created and what is in them.

    Click for the solution

    The modified script:

    scripts/sleep.sh
    #!/bin/bash
#SBATCH --account=PAS3493
#SBATCH --time=1
set -euo pipefail

echo "I will sleep for 100 seconds" > sleep.txt

sleep 100s

echo "I'm awake! Successfully finished script sleep.sh"

    Submit it:

    sbatch scripts/sleep.sh
    Submitted batch job 23641567

    After a little over a minute, the job is gone from the squeue output. Both sleep.txt and a Slurm log file were created:

    cat sleep.txt
    I will sleep for 100 seconds
    cat slurm-23641567.out
    slurmstepd: error: *** JOB 23641567 ON p0133 CANCELLED AT 2026-10-28T14:06:24 DUE TO TIME LIMIT ***

    The “I’m awake!” line is missing, because Slurm killed the job during sleep.

  2. How does this outcome compare to that of the job you canceled in the previous lecture’s Exercise 3?

    Click for the solution

    Hardly at all: in both cases, the job was killed during sleep, so sleep.txt was produced, but the “I’m awake!” line was not. The only differences are that this time, Slurm killed the job instead of you, and that the error message in the Slurm log file mentions the time limit.

    This is why a final “Successfully finished” line in your scripts is so useful: if it’s missing from the Slurm log file, you know the script didn’t finish, no matter what stopped it.

Finally, remove the generated files:

rm slurm* sleep.txt

3 Batch job examples with FastQC

In week 7, we used a for loop to run FastQC for every FASTQ file, one after the other. This ran quickly, but keep in mind that our practice FASTQ files are only 5% of their original sizes. Additionally, other bioinformatics programs may take much longer, even for small files. To speed things up, and not block the terminal while programs are running, we will submit a batch job for each sample/file, so that many jobs can run simultaneously1.

So, let’s practice with submitting a batch job for each FastQC run. We’ll first submit a job for a single file, and then loop over all files to submit many jobs. You should have the FastQC script in scripts/fastqc.sh.

3.1 Modify the script for usage with Slurm

Here, you’ll add Slurm options to the script with #SBATCH lines, and consider whether FastQC should use multiple cores. When you have multiple cores at your disposal in a batch job, you should almost always explicitly tell the program how many cores it can use. Some programs default to using 1 core while others try to auto-detect the number of cores, but any auto-detection tends to be inappropriate at OSC2.

Exercise 2: Add Slurm options to the FastQC script

  1. Add #SBATCH lines to the top of scripts/fastqc.sh, so that:

    • The OSC project PAS3493 will be billed
    • You’ll get an email only if the job fails
    • The Slurm log file will be named slurm-fastqc-<job-id>.out

    Click for the solution

     
    scripts/fastqc.sh (excerpt)
    #!/bin/bash
#SBATCH --account=PAS3493
#SBATCH --mail-type=FAIL
#SBATCH --output=slurm-fastqc-%j.out

  2. Should you also reserve multiple cores for these FastQC batch jobs? Here is the description of FastQC’s option for multi-threading, from its help info:

    -t --threads    Specifies the number of files which can be processed
                simultaneously.  Each thread will be allocated 250MB of
                memory so you shouldn't run more threads than your
                available memory will cope with, and not more than
                6 threads on a 32 bit machine

    Given that each of our batch jobs will process a single FASTQ file, would, say, 4 cores and --threads 4 make each job faster?

    Click for the solution

    No: FastQC uses one thread per file, so with a single file per job, 3 of the 4 cores would sit idle — while your project would still be billed for all 4. So, for this script, we’ll stick to the default of 1 core.

    This is quite specific to FastQC: most programs, like TrimGalore (which you used in Graded Assignment 4), can use multiple cores to process a single (pair of) file(s) faster. Always check what a program’s “threads” or “cores” option actually does!

3.2 A single test batch job

Submit the batch job

Now, you’re ready to submit the script. Let’s test it for one sample first:

sbatch scripts/fastqc.sh ../garrigos/fastq/S63_R1.fastq.gz results/fastqc
Submitted batch job 37615710

Monitor the batch job

Next, monitor your job by checking its status in the Slurm queue:

squeue -u $USER -l
Wed Oct 28 14:31:48 2026
             JOBID PARTITION     NAME     USER    STATE       TIME TIME_LIMI  NODES NODELIST(REASON)
          37615710   cpu-exp fastqc.s   jelmer  RUNNING       0:01   1:00:00      1 p0510

After a while:

  • You will know that your job has stopped running (either due to failure or because it finished successfully) when it is no longer listed in the squeue output.
  • If you additionally didn’t receive an email from Slurm, this suggests the job succeeded — job failure should have triggered an email due to the #SBATCH --mail-type=FAIL line.

Check the output files

Even if you’ve inferred that your job succeeded from the abovementioned clues, don’t forget to look at the output files to confirm this:

  • Slurm log file: The combination of having strict bash set settings and the “Successfully finished” echo line at the end of the script means that if you see that line printed, the script encountered no errors. Nevertheless, you should also look at the rest of this file, because a program’s “logging statements” may have useful information, including output summaries but also warnings.

  • The program’s main output files: As discussed, most bioinformatics tools don’t just print “logging” information that ends up in the Slurm log file, but will also have output files (in the case of FastQC, an HTML and a Zip file). Therefore, always check the output dir for the presence of such output files.

Check that the Slurm log file ends with the “marker” line that indicates a successful run:

# (You can also Tab-complete your filename instead)
tail slurm-fastqc*.out
Approx 90% complete for S63_R1.fastq.gz
Approx 95% complete for S63_R1.fastq.gz
Approx 100% complete for S63_R1.fastq.gz
Analysis complete for S63_R1.fastq.gz

Used FastQC version:
INFO:    Using cached SIF image
INFO:    gocryptfs not found, will not be able to use gocryptfs
FastQC v0.12.1

Successfully finished script fastqc.sh
Wed Oct 28 02:31:51 PM EDT 2026

(With a real analysis, you’d also want to read through the whole file, e.g. with less.)

TipOptional: hide Apptainer’s INFO messages in your Slurm log files (Click to expand)

When you run a program with apptainer exec, Apptainer prints some messages of its own, like “INFO: gocryptfs not found, will not be able to use gocryptfs”. These are harmless, but clutter your Slurm log files. To hide them, add the --quiet option right after apptainer (warnings and errors will still be shown):

scripts/fastqc.sh (excerpt)
apptainer --quiet exec "$CONTAINER" fastqc --outdir "$outdir" "$fastq"

Finally, check for the presence of the main FastQC output files:

ls -lh results/fastqc
total 1.1M
-rw-rw----+ 1 jelmer PAS0471 718K Oct 28 14:31 S63_R1_fastqc.html
-rw-rw----+ 1 jelmer PAS0471 364K Oct 28 14:31 S63_R1_fastqc.zip

It can also be a good idea to pay attention to the file sizes of outputs, as shown by ls -lh. Especially if you’re not going to open the output files right away, this can be yet another clue as to whether the program succeeded. When they fail, some programs produce empty or extremely small output files — their presence should always be a red flag.

Clean up

Because this was a test-run, and you will now run a loop to analyze each sample, let’s remove the outputs:

rm -r results/fastqc slurm-fastqc*

In this case, it is useful to keep these files around somewhere, as they contain information about our runs (when, which files, what version, etc.). But we want to move them out of our working dir. It often makes sense to store them in a subdir of the program’s outdir, e.g.:

mv slurm-fastqc-* results/fastqc/logs/

To avoid moving log files by hand, you can also make your script put a copy of its Slurm log file in the output dir: see this section of the optional self-study page on Slurm.

3.4 Recap: Making sure your jobs ran successfully

To recap, here is an overview of basic strategies to monitor your batch jobs:

  • To see whether your job(s) have started, check the queue (with squeue) and/or check for Slurm log files (with ls).

  • Once the jobs are no longer listed in the queue, they will have finished: either successfully or because of an error.

  • When you’ve submitted many jobs that run the same script for different samples/files:

    • For at least one of the jobs, carefully read the full Slurm log file, and check other output files.
    • Check that no jobs have failed: via email when using --mail-type=FAIL, and/or by checking each log for messages like “Successfully finished script” (run grep -c on all logs at once).
    • Check that you have the expected number of output files (run ls | wc -l) and that no files have size zero (run ls -lh).
TipJob monitoring tip: See output added to the Slurm log file in real time (Click to expand)

Text will be added to the Slurm log file in real time as the running script (or the program run by the script) outputs it. However, the output printed by commands like cat and less is static and not updated in real-time.

Therefore, if you find yourself opening/printing the contents of the Slurm log file again and again to keep track of the job’s progress, then instead use tail -f, which will “follow” the file and will print new text as it’s added to the Slurm log file:

# See the last lines of the file, with new contents added in real time
tail -f slurm-fastqc-37615717.out

To exit the tail -f livestream, press Ctrl+C.

## Shell script conventions

- Start scripts with `#!/bin/bash` and `set -euo pipefail`
- Below that, add a comment block with the script's purpose and a usage line
  (e.g. `# Usage: bash scripts/fastqc.sh <FASTQ file> <output dir>`)
- Copy arguments to descriptively named, lowercase variables (e.g. `fastq="$1"`);
  use uppercase only for constants (e.g. `CONTAINER=...`)
- At the start, report the script name, the date, and the inputs;
  at the end, report the program version, a success message, and the date
- Create output dirs with `mkdir -p` before writing to them
- Strike a balance between script functionality and robustness vs. simplicity and
  readability: I am a shell beginner
- In script comments, briefly explain any non-obvious commands, options, and constructs
- Programs that aren't available in the system path should be run with Apptainer
  containers from Seqera Containers (`oras://` URLs),
  not with `module load` or by installing them

5 Zooming out: workflows

5.1 Multi-step workflows

In a typical omics project (and likely in your final project for this course), you need to run multiple consecutive steps to process and analyze your data: you have a “workflow”. So far, we have focused on running individual steps, like FastQC. How do you organize and run your workflow as a whole?

Recall this RNA-seq workflow, going from raw reads to gene counts:

As discussed in week 2, it is a good idea to keep separate Markdown files for:

  • A “lab notebook” with chronological entries of everything you did, including mishaps and dead ends.
  • A “protocol” with the final code in order of execution, needed to rerun your project’s entire computational work.

5.2 A protocol example

Here is a (hypothetical) protocol for the workflow above3. Each step runs a single-step script that takes in- and output files as arguments, and is submitted as one or more batch jobs:

protocol.md
# RNA-seq analysis of _Culex pipiens_

- Author: Jane Doe
- Date: 2026-10-28
- This was run at the Ohio Supercomputer Center (OSC)

## Set up: Set the input file paths

```bash
fastq_dir=data/fastq
ref_assembly=data/ref/assembly.fna
ref_transcripts=data/ref/transcripts.fna
```

## Step 1: Read QC with FastQC

`fastqc.sh` runs FastQC on 1 FASTQ file,
and takes 2 arguments: the FASTQ file and the output dir.

```bash
for fastq in "$fastq_dir"/*fastq.gz; do
    sbatch scripts/fastqc.sh "$fastq" results/fastqc
done
```

## Step 2: FastQC summary with MultiQC

`multiqc.sh` runs MultiQC once for all FastQC outputs,
and takes 2 arguments: the input dir (the FastQC output dir) and the output dir.

```bash
sbatch scripts/multiqc.sh results/fastqc results/multiqc
```

## Step 3: Read trimming with TrimGalore

`trimgalore.sh` runs TrimGalore on the paired-end FASTQ files of 1 sample,
and gives the output files the same names as the input files.
It takes 3 arguments: the R1 FASTQ file, the R2 FASTQ file, and the output dir.

```bash
for fastq_r1 in "$fastq_dir"/*_R1.fastq.gz; do
    fastq_r2=${fastq_r1/_R1/_R2}
    sbatch scripts/trimgalore.sh "$fastq_r1" "$fastq_r2" results/trimgalore
done
```

## Step 4: Alignment to a reference genome with STAR

`star.sh` aligns the trimmed reads of 1 sample to the reference genome,
and takes 4 arguments: the trimmed R1 and R2 FASTQ files,
the reference genome FASTA file, and the output dir.

```bash
for fastq_r1 in results/trimgalore/*_R1.fastq.gz; do
    fastq_r2=${fastq_r1/_R1/_R2}
    sbatch scripts/star.sh "$fastq_r1" "$fastq_r2" "$ref_assembly" results/star
done
```

## Step 5: Gene-level counting with Salmon

`salmon.sh` counts the reads per gene for 1 sample,
and takes 3 arguments: the BAM file from STAR, the reference transcript FASTA file,
and the output dir.

```bash
for bam in results/star/*bam; do
    sbatch scripts/salmon.sh "$bam" "$ref_transcripts" results/salmon
done
```

Structuring your workflow like this makes it relatively straightforward to rerun everything (e.g. with different samples or settings), or to reuse it in another project. And the protocol documents all steps that were taken.

However, you cannot run all of this code at once:

Why can’t all the code be run at once?

Most steps need files produced by an earlier step as their input. If you run all code at once, all batch jobs will be submitted at the same time, so later steps will start running before their input files are available, and will fail.

Which steps can be run simultaneously?

Steps 1 (FastQC) and 3 (TrimGalore), because both use the raw FASTQ files as input and therefore don’t depend on each other. Every other step needs the output of a preceding step.

5.3 How about automation?

There are two main ways to automate such a workflow further:

  1. With more advanced Bash and Slurm code, e.g. by combining multiple steps into one script, or by using Slurm “job dependencies” so that jobs only start once the jobs they depend on have finished successfully4. However, the added complexity of such scripts often doesn’t pay off in the time you save (see the optional Slurm self-study page for some examples).

  2. With a “workflow management system”, which provides a way to formally describe and execute pipelines. The two most commonly used ones in bioinformatics are Nextflow (Di Tommaso et al. 2017) and Snakemake (Mölder et al. 2025). These can e.g. automatically submit Slurm jobs, rerun only the steps affected by changes or failures, and run the same pipeline on different computers and datasets. Their main disadvantage is a somewhat steep learning curve.

My recommendation is therefore to either:

  • Accept that your workflow isn’t fully automated and use a Markdown protocol like the one above
  • Go all-in and use a workflow management system (specifically, Nextflow). This has become a lot more accessible with genAI, and is an excellent use case for genAI, because you can check its work: if you already have a working protocol, you can run the genAI-written pipeline and compare its outputs to those of your protocol.

5.4 Pre-existing pipelines

Also keep in mind that you don’t always have to build your own pipeline. Many publicly available pipelines exist, and Nextflow has by far the best ecosystem of these: the “nf-core” initiative (Ewels et al. 2020) curates over 150 best-practice, flexible, and well-documented Nextflow pipelines, developed over years by many experts in the field. This saves you from having to figure out which of the many available tools and settings to use.
