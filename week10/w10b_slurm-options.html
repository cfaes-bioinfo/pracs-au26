Common sbatch options

We’ll go through the most commonly used sbatch options (except --account; previous lecture).

Recall that any sbatch option can be:

  • Passed on the command line: sbatch --account=PAS3493 myscript.sh

  • Added at the top of the script you’re submitting:

    myscript.sh (excerpt)
    #!/bin/bash
#SBATCH --account=PAS3493

Precedence and long vs. short format

  • If an option is specified in both places, the command-line option takes precedence.
  • Many options have a long (e.g. --account=) and a short format (e.g. -A).
    For clarity, we’ll stick to long-format options in this material.

Time limits: introduction

  • The default time limit is 1 hour.

  • You can request up to 7 days of time
    (or ask OSC for access to a different queue for longer jobs).

  • Your job will be killed as soon as it hits the time limit!

The time you reserve is the “wall time”

This is simply the amount of time that passes on the (wall) clock. In contrast, “core hours” are the wall time multiplied by the number of cores.

A job that runs for 2 hours on 8 cores has a wall time of 2 hours and uses 16 core hours.

  • OSC bills for the time that jobs actually used, not what you reserved, and jobs stop as soon as the script has finished running.

  • It’s often not clear how long a job will take, so it’s common to request (substantially) more time than your best guess.

  • But keep in mind that jobs requesting more time are likely to wait longer before they start (fortunately, OSC tends to have short queueing times).

Time limits: how to specify

The --time option specifies the maximum wall time for your job.
A number of formats can be used to specify the amount of time, including:

Format Example Meaning
minutes 60 60 minutes
hours:minutes:seconds 1:00:00 60 minutes
days-hours 2-12 2.5 days (60 hours)


For example, requesting 2 hours in the “minute-format” inside a shell script:

myscript.sh (excerpt)
#!/bin/bash
#SBATCH --time=120

Cores with --cpus-per-task

  • Slurm uses the terms “core” and “CPU” interchangeably, and bioinformatics tools often say “thread”: therefore think of core, CPU, and thread as synonyms.

  • Running a program with multiple cores is very common, and can make it run much faster.
    8–12 cores is often a sweet spot (more can suffer from strongly diminishing returns).

  • Use --cpus-per-task, and also tell the program how many cores it can use:
myscript.sh (excerpt)
#!/bin/bash
#SBATCH --cpus-per-task=8

# We tell a fictional program about the number of available cores:
trimmer.py --cores 8 sampleA_R1.fastq.gz

Memory with --mem

  • The --mem option sets the maximum amount of memory (RAM) available to your job.
  • The default is about 4 GB per core: e.g., --cpus-per-task=4 gives you 16 GB of memory.
    Therefore, you’ll often have enough memory automatically, and may not need to specify --mem.
  • Like with time, your job is killed when it hits the memory limit (but the error messages are less clear).
  • The default --mem unit is MB (MegaBytes): append G for GB. For example, to request 20 GB:
myscript.sh (excerpt)
#!/bin/bash
#SBATCH --mem=20G


Regular Pitzer nodes have up to 178 GB of memory. To request more, see the optional self-study page.

Slurm log file names with --output

  • By default, the Slurm log file is created in the dir from which you submitted the script,
    and is called slurm-<job-id>.out, e.g. slurm-12431942.out.

  • It can be useful to include the purpose of the script in the Slurm log file name,
    typically by including the name of the program that the script runs. For example:

    fastqc.sh (excerpt)
    #!/bin/bash
#SBATCH --output=slurm-fastqc.out

Slurm log file names with --output

fastqc.sh (excerpt)
#!/bin/bash
#SBATCH --output=slurm-fastqc.out


But what can be a problem with the above Slurm log file name?

For example, consider a scenario where you submit a batch job for each FASTQ file with a loop:

for fastq_file in ../garrigos/fastq/*fastq.gz; do
    sbatch scripts/fastqc.sh "$fastq_file" results/fastqc
done
    Click for the answer

All jobs write to the same log file, slurm-fastqc.out, so they overwrite each other’s output. You’ll end up with a single log file that contains the output of only one job, or a jumble of output from several jobs.

Slurm log file names: include the job ID

  • You’ll want to keep the job ID in the log file name, so log files from different jobs differ and don’t overwrite each other.

  • But how, since you won’t know the job ID in advance? The %j placeholder represents the job ID:

    myscript.sh (excerpt)
    #!/bin/bash
#SBATCH --output=slurm-fastqc-%j.out

  • This produces files like slurm-fastqc-56605102.out and slurm-fastqc-56605103.out.

Why not specify a directory for the log file?

You could use --output=results/fastqc/slurm-fastqc-%j.out to put the log files in a subdir.
This may seem convenient, but I personally don’t recommend it.

For example, that dir must already exist when you submit the job, and it becomes easy to overlook the log files if you submit many jobs at once. See the optional self-study page for more considerations and options.

Notification emails with --mail-type

Slurm can email you when a job begins, completes successfully, or fails —
it automatically uses the address linked to your OSC account. I recommend the following:


Shorter jobs (up to a few hours)

Only get emails if they fail:

myscript.sh (excerpt)
#!/bin/bash
#SBATCH --mail-type=FAIL
  • FAIL because you may otherwise overlook failures for some jobs (especially when you submit many jobs at a time).
  • No END because emails will become overwhelming and easy to ignore.

Longer jobs (> a few hours)

Get emails when they fail or finish:

myscript.sh (excerpt)
#!/bin/bash
#SBATCH --mail-type=END,FAIL
  • You don’t want to have to keep checking in on jobs that run for many hours, so it’s useful to get an email also when they finish.
