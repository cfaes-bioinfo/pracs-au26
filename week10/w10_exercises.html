Introduction

Overview

In Graded Assignment 4, you wrote a shell script to run TrimGalore on the FASTQ files of one sample. You ran it directly with bash, using 1 core, and then ran it for 7 samples one after the other with a for loop.

In these exercises, you’ll take that script one step further:

  • In Exercise 1, you’ll turn it into a script that you can submit as a batch job, using multiple cores.
  • In Exercise 2, you’ll submit a batch job for every sample at once, using a loop in a protocol Markdown file, and check that all jobs succeeded.
  • In Exercise 3, you’ll complete your protocol for the first steps of the RNA-seq workflow.
  • In Exercise 4, you’ll have Claude write a script to run SeqKit as a batch job, and check its work.

  1. Add #SBATCH lines to the top of your TrimGalore script to specify:

  2. In GA4, you didn’t change TrimGalore’s number of cores, because you only had 1 core available. Now that your batch job will have 8 cores, find the TrimGalore option that sets the number of cores in its help info. Then, edit the trim_galore command in your script to use all 8 reserved cores. Based on the option’s description, would it be worth reserving 16 cores instead, to make the job twice as fast?

      Click to see the solution

    Print the help info (only relevant output lines shown below):

    apptainer exec oras://community.wave.seqera.io/library/trim-galore:2.3.0--a56e49e832976df4 \
    trim_galore --help
      -j, --cores <CORES>
          Number of worker threads for parallel processing (default: 1).
          At --cores 1 the worker-pool is bypassed (single thread, ~5 MB RAM).
          From --cores 2 upward, an N+4 thread model applies: N workers +
          2 decompressors + 1 batcher + 1 writer.
          Wall-clock speedup is near-linear up to --cores 8 for paired-end runs;
          beyond that, gzip-output I/O on the storage layer typically becomes
          binding before workers run out of useful per-read work,
          so additional cores help progressively less

    The option is -j/--cores. Unlike FastQC’s --threads option, which only parallelizes the processing of multiple files, TrimGalore can also use multiple cores to process a single pair of files faster. So, edit the trim_galore command as follows:

    apptainer exec "$TRIMGALORE_CONTAINER" \
    trim_galore \
    --cores 8 \
    --paired \
    --fastqc \
    --output_dir "$outdir" \
    "$fastq_r1" \
    "$fastq_r2"

    Reserving 16 cores would probably not be worth it: according to the help info, the speedup is near-linear up to 8 cores, but beyond that, additional cores help “progressively less”. So, the job would be less than twice as fast, while your project would be billed for twice as many cores.

    You may also notice that with --cores 8, TrimGalore runs 4 additional “helper” threads, e.g. to read and write the FASTQ files. That’s fine: Slurm restricts your job to the 8 reserved cores, so these threads simply share them, and setting --cores to the number of reserved cores remains a good rule of thumb.

    Finally, keep in mind that our practice FASTQ files are so small that the job will be quick either way, so you may not notice much of a speedup compared to your 1-core runs in GA4. With full-size FASTQ files, multiple cores make a much bigger difference.

  2. In the lecture’s protocol, the STAR step loops over the output files of the TrimGalore step. Say the TrimGalore job for one sample failed, and you didn’t notice. What would happen when you run the STAR step? Why is this worse than getting an error?

      Click to see the solution

    The STAR loop would simply skip the failed sample, because its trimmed FASTQ files don’t exist. You wouldn’t get any error: all STAR jobs would succeed, and you’d just end up with one sample fewer in your count table.

    You may not notice this until much later. This is why you should check that all jobs of a step succeeded before moving on, e.g. by counting the output files like you did in Exercise 2.

  3. Say you notice that the TrimGalore job for one sample failed, and you fix the problem. Which steps of the lecture’s protocol would you then need to rerun, and for which samples? Could you simply rerun the code blocks in the protocol for those steps?

      Click to see the solution

    You’d need to rerun TrimGalore and the steps that use its output, STAR and Salmon, but only for the failed sample. FastQC and MultiQC use the raw FASTQ files, so they are not affected.

    You shouldn’t simply rerun the protocol’s loops, because those would submit jobs for all samples again. Instead, submit single jobs for the failed sample, e.g. for sample S63:

    sbatch scripts/trimgalore.sh \
    "$fastq_dir"/S63_R1.fastq.gz "$fastq_dir"/S63_R2.fastq.gz results/trimgalore

    And once that job has finished, do the same for the STAR step, and then for the Salmon step. This is one advantage of scripts that process a single sample: you can easily rerun just the part of the workflow that failed.

Exercise 4: A SeqKit batch job script with Claude

SeqKit is a toolkit for FASTA and FASTQ files. Its seqkit stats command reports, for each input file, the number of reads, the total number of bases, and the read lengths. You’ll have Claude write a script that runs seqkit stats on all FASTQ files in a dir as a single batch job, and then check that script carefully.

  1. If you haven’t done so already, make sure you have an updated CLAUDE.md in your week10 dir (see w10b here).

  2. In a new Claude conversation, with the permission mode set to Manual, ask Claude to write the script, for example:

    Write a script scripts/seqkit_stats.sh that runs seqkit stats on all FASTQ files in an input dir, using 4 cores, and writes the results to a TSV file in an output dir. The input dir and output dir should be arguments. Don’t run it.

  3. Check the script and get a container link before running it:

    • Does it follow the conventions in your CLAUDE.md, including the #SBATCH lines?
    • Does the number of threads that SeqKit is told to use match --cpus-per-task?
    • How did it deal with SeqKit: did it want to use a container, and if so how? Regardless, you will need to obtain a container link from the Seqera Containers website yourself, and put it in the script.
    • Did Claude add any other #SBATCH options or lines you don’t recognize? If so, find out what they do.

      Click to see the solution

    Claude’s script will vary, but it should look similar to this:

    scripts/seqkit_stats.sh
    #!/bin/bash
#SBATCH --account=PAS3493
#SBATCH --cpus-per-task=4
#SBATCH --mail-type=FAIL
#SBATCH --output=slurm-seqkit_stats-%j.out
set -euo pipefail

# Script to run seqkit stats on all FASTQ files in an input dir,
# and write the results to a TSV file in an output dir
# Usage: sbatch scripts/seqkit_stats.sh <input dir> <output dir>

# seqkit container
# NOTE: replace this with the actual URL from https://seqera.io/containers/
# (search for "seqkit"); I could not look up the exact build hash
CONTAINER=oras://community.wave.seqera.io/library/seqkit:<VERSION>--<HASH>

# Number of cores (should match --cpus-per-task above)
THREADS=4

# Copy the placeholder variables
indir="$1"
outdir="$2"

# Initial logging
echo "Starting script seqkit_stats.sh"
date
echo "Input dir:    $indir"
echo "Output dir:   $outdir"
echo

# Create the output dir if needed
mkdir -p "$outdir"

# Define the output file
outfile="$outdir/seqkit_stats.tsv"

# Run seqkit stats with its container:
# --tabular: output in TSV format (instead of a human-readable table)
# --threads: number of cores to use
# The glob (*.fastq.gz) expands to all gzipped FASTQ files in the input dir
apptainer exec "$CONTAINER" \
    seqkit stats \
    --tabular \
    --threads "$THREADS" \
    "$indir"/*.fastq.gz \
    > "$outfile"

# Final logging
echo
echo "Used seqkit version:"
apptainer exec "$CONTAINER" seqkit version
echo
echo "Output file:  $outfile"
echo "Successfully finished script seqkit_stats.sh"
date

    • The value of --threads should match --cpus-per-task. (If Claude left out --threads, SeqKit would still use 4 threads, its default, but it’s better to be explicit, as your CLAUDE.md asks.)

    • Unlike FastQC in the w10b jobs, multiple cores do help here: this single job processes all 44 FASTQ files, and SeqKit uses its threads to process multiple files in parallel.

    • The example above does not have the container link yet — one valid link is: oras://community.wave.seqera.io/library/seqkit:2.14.0--242173bf1fbab6c9.

Bonus: Rename the output FASTQ files

The TrimGalore output FASTQ files are oddly named, ending in _R1_val_1.fq.gz and _R2_val_2.fq.gz. This is not necessarily a problem, but could trip you up in a later step. For example, the STAR loop in the lecture’s protocol looks for trimmed files ending in _R1.fastq.gz, which is why the TrimGalore script in that protocol renames its output files.

  1. Modify your TrimGalore script to rename the output FASTQ files after running TrimGalore, giving them the same names as the input files. Then, resubmit the script for sample S63 to check that your changes work, using a separate output dir like results/trimgalore_test.

      Click to see the solution

    Add the following code to your script, after the trim_galore command:

    scripts/trimgalore.sh (excerpt)
    # Rename the output FASTQ files to the same names as the input files
sample_id=$(basename "$fastq_r1" _R1.fastq.gz)
R1_out_init="$outdir"/"$sample_id"_R1_val_1.fq.gz
R2_out_init="$outdir"/"$sample_id"_R2_val_2.fq.gz
R1_out_final="$outdir"/"$sample_id"_R1.fastq.gz
R2_out_final="$outdir"/"$sample_id"_R2.fastq.gz

mv -v "$R1_out_init" "$R1_out_final"
mv -v "$R2_out_init" "$R2_out_final"
    • basename with a second argument removes that suffix from the file name, so ../garrigos/fastq/S63_R1.fastq.gz becomes S63.
    • Alternatively, you could use $(basename "$fastq_r1") to get S63_R1.fastq.gz, and use that directly as the final R1 file name.
Hints (Click to expand)

To rename the files, you first need to extract and store the part of the file name that is basically a sample ID: the part before _R1.fastq.gz/_R2.fastq.gz. To do that, you will need to use “command substitution” and the basename command. Those are explained on the optional advanced shell scripting self-study page starting here, but we did not cover them together in class.

Here is a skeleton of the code to extract that part of the file name:

# Replace " ... " with your code.
sample_id=$( ... )

Based on that ID, you can build up the names of the TrimGalore output files and those of the desired final file names. For example:

# The name of the initial ('init') TrimGalore R1 output file will be:
R1_out_init="$outdir"/"$sample_id"_R1_val_1.fq.gz

See also this section on renaming files with loops, though realize that this situation is different, because you will do the renaming inside the script without a loop.
