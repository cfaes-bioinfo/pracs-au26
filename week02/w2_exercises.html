  • One problem with the order of the parts of a link.

The problems were:

  1. No space after the # of the title, so it isn’t a header.
  2. No blank line between the paragraph and the list below it. VS Code’s preview is forgiving and still shows a list here, but stricter renderers (including Quarto’s, which you’ll use from week 12) will not — so always leave the blank line.
  3. No space after the - of the second list item, so it isn’t a list item and is added to the previous one instead, one the same line.
  4. The link has its two parts reversed: the [link text] comes first, and then the (URL).
  5. The inline code for notes.md has an opening backtick but no closing one, so it doesn’t show up as inline code in the preview.
  6. **really* has two asterisks on one side and only one on the other. Only one asterisk on each side is used, so you get italic instead of bold, with a leftover (literal) * in the output.
  7. No blank line before the ## Things to try next week header. Again, VS Code’s preview accepts this, but not every renderer will.
  8. The bash/date code block lost its triple backticks, so it shows up as regular text and as a single line. Note: Within a code block, you do not need blank lines to avoid merging lines together! Since there are no “paragraphs” in a code block, the renderer will not merge lines together.
  9. The table is missing the row of dashes below the header row, so it isn’t rendered as a table, and once again is collapsed into a single line.

Finally, the two sentences “I started a VS Code session at OSC.” and “Then I opened a Markdown file.” are on separate lines in the source but end up in one line in the output: a single line break is ignored. While notable, this isn’t necessarily a problem, and you may in fact deliberately write Markdown with short lines like this, so that the source is easier to read. But in the fixed file below, we assumed that the two sentences were meant to be two paragraphs, and we added a blank line between them.

Exercise 3: File names

Create a file 3_file-names.md in your week02/exercises folder. For each of the file names below, write in your file:

  • The original name (as inline code)
  • A better name (as inline code)
  • One line about what was wrong with the original
  1. sample2_R1.fastq — from a folder that also contains sample10_R1.fastq and will eventually hold files for 40 samples
  2. RNAseq counts FINAL.csv
  3. plot1.png — for a plot showing a Principal Component Analysis of all samples
  4. 2019_3_7_field_notes.txt
  Click to see the solution

Several other answers are possible — what matters is that your names are machine-readable, human-readable, and sort correctly.

  1. sample2_R1.fastq → sample02_R1.fastq
    Without a leading zero, sample10 sorts before sample2. With 40 samples, two digits are enough.

  2. RNAseq counts FINAL.csv → rnaseq-counts.csv
    The spaces are not machine-readable, and capitals are best avoided too. While there is some nuance here, you should generally also avoid qualifiers like “FINAL” (would the next version be “FINAL2”?). Instead, be more specific and/or use version control (week 5 of this course).

  3. plot1.png → pca_all-samples.png
    The original is machine-readable but not human-readable: it says nothing about what the figure shows.

  4. 2019_3_7_field_notes.txt → field-notes_2019-03-07.txt
    The date needs leading zeros and hyphens to sort correctly, and underscores are better reserved for separating units (here: the date from the description).

Exercise 4: A project folder

In this exercise, you’ll build the skeleton of a research project folder, with placeholder files and a README.md. Start by picking one of the two project options below.

  • Option A: Your own project
  • Option B: A fictional RNA-seq project

Use a research project of your own; either one you are working on now, or one you expect to start soon.

Only pick this option if you can name about ten files that the project has or will have, and can say several things about its data: where it came from, when, and from whom.

Since this is just for practice, it’s fine if you make up some placeholder/dummy file names and details, but if you feel like you’d have to make up too much, use Option B instead.

You are studying how drought stress affects gene expression in maize (Zea mays).

You grew 24 plants (12 well-watered “control” plants and 12 drought-treated plants) and harvested leaf tissue from each plant. The CFAES Molecular Biology and Genomics Core prepared and sequenced the RNA-seq libraries, and you downloaded the raw sequence data from them on May 1, 2026. The next day, you downloaded the maize reference genome (assembly GCF_902167145.1) from NCBI.

These are the files you have so far:

  • SampleSheet Final.xlsx — the spreadsheet from the sequencing facility with sample IDs, treatments, and harvest dates
  • ctrl01_R1.fastq.gz and ctrl01_R2.fastq.gz — raw reads for control plant 1
  • drought10_R1.fastq.gz and drought10_R2.fastq.gz — raw reads for drought-treated plant 10
  • GCF_902167145.1_genomic.fna — the reference genome you downloaded
  • 01_align-reads.sh — a script that aligns the reads to the reference genome
  • counts.csv — the gene count table produced by that script
  • 02_plot-counts.R — a script that makes figures from the count table
  • Fig 1 FINAL v3.png — a PCA plot of all samples, made by that script
  • diary.md — your lab notebook, with an entry for each day you worked on the project

Final notes:

  • You also have the reads for the other 22 plants, but there is no need to list all of those.
  • _Most of these names are already fine: only two of them need to be changed.

    Some things to note about where the files go:

    • The sample sheet is a form of data so it belongs in data rather than in doc. In omics projects where the omics data is the main source of data, we often consider such sample information “metadata”, so it can go in data/meta.
    • counts.csv is produced by one of your scripts, which makes it a result, even though the next script uses it as input.
    • The reference genome is data that you downloaded rather than generated, so it goes in data too. But in its own subfolder, since it is not data about your samples.
    • The lab notebook is documentation, so diary.md goes in doc.

    And about the two files that had to be renamed:

    • SampleSheet Final.xlsx → samples.tsv
      The spaces and capitals make it hard to work with, “Final” says nothing about the content, and the file should be converted from Excel to a plain-text format.
    • Fig 1 FINAL v3.png → pca_all-samples.png
      Again spaces and capitals, and the name says nothing about what the figure shows. Keeping track of versions in the file name is what version control is for (week 5).

    The other names were already fine. Note that the scripts are numbered, which shows the order in which they should be run, and that the sample numbers have a leading zero (ctrl01 rather than ctrl1) so that they will sort correctly.
