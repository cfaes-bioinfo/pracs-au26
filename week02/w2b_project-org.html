File organization and management

Recommended practices

  1. Use one folder (folder hierarchy) for one project
  2. Separate different kinds of files using a consistent subfolder structure
  1. Avoid (manual) editing of your data and your results
  2. Follow file and folder naming practices that favor machine- and human-readability
  3. Use so-called “relative paths” to refer to files and folders within your project

Let’s get into these!

1. Use one folder for one project

  • All files for one project should be contained in one folder hierarchy – and make liberal use of subfolders!
  • Don’t scatter files from one project across your computer

This makes it easier to:

  • Find files
  • Share or back up your entire project
  • Avoid throwing away stuff in error

See the lecture notes for a discussion of how to handle shared data or code between projects.

Two project folder hierarchies. Each box is a folder.

2. Separate files using a consistent structure

Use subfolders to separate, for example:

  • Code
  • Data
  • Results (of data processing and analysis)

3. Avoid (manual) editing of data and results

  • Raw data files should never be edited once produced
  • Avoid manually editing files such as intermediate results — do this with code instead

Treatment of data versus results

  • Raw data: read-only (never edit the originals!) and highly valuable (make backups!)
  • Results: essentially disposable – you should be able to regenerate them easily

4. Use machine- and human-readable file names

Three key principles (Jenny Bryan) — file names should be:

  1. Machine-readable
  2. Human-readable
  3. Ordered correctly by default alphanumeric sorting

4a. Machine-readable names

  • Don’t use spaces in file names
  • Only use: letters/numbers (A-Za-z0-9), underscores (_), hyphens (-), periods (.)
  • Where appropriate, include metadata like sample ID, date, and treatment:
    • sample032_2016-05-03_low.txt
    • samples_soil_treatmentA_2019-01.txt

4b. Human-readable names

“Name all files to reflect their content or function. For example, use names such as bird_count_table.csv, manuscript.md, or sightings_analysis.py.” (Wilson et al. 2017)

One good scheme:

  • Use underscores (_) to delimit units: sampleID, batch, treatment, date
  • Use dashes (-) to delimit words within a unit: grass-samples
  • Limit periods (.) to file extensions
  • Generally avoid capitals
mmus001_filtered-by-mq30_sorted.bam
mmus002_filtered-by-mq30_sorted.bam

4c. Names that sort correctly

  • Dates: write as YYYY-MM-DD (e.g., 2020-10-11) — sorts correctly and is unambiguous

Documenting your research project

Why document your work?

  • It’s not always easy – documenting can feel like a waste of time when something then and there seems obvious
  • But you won’t have a clear picture a month later, and a collaborator won’t either

Tip

Make a conscious effort to take a step back, slow down, and write down what you did and why.

Code is self-documenting to a large extent – but that shouldn’t make you complacent about documenting your work!

Maintain README and other documentation files

Documentation should contain all information needed to reproduce your research, e.g.:

  • Where/when/how each data and metadata file originated
  • Versions of software, databases, reference genomes

Three types of documentation files

README
(top-level, always!)

  • Project overview
  • Folder structure & file naming
  • Data details
  • Contact info

Lab notebook
(doc/diary.md, by date)

  • What you did and why
  • Not “clean” – keep failed attempts too

Workflow/protocol
(doc/workflow.md, by execution order)

  • Code to rerun final analyses
  • Should be “clean”

Use plain-text files

  • We’ll work almost exclusively with plain-text files (e.g. .txt) – can be opened by any text editor on any computer
  • Contrast with binary/proprietary formats like .xlsx or .docx

Plain-text files are preferable for reproducible science because they:

  • Can be accessed on any computer, including remotely
  • Can be operated on by Unix shell commands and any programming language
  • Are future-proof
  • Can be version-controlled appropriately

Tip

You’ll use Markdown (.md) files – a nice balance between ease of writing/reading and formatting options. More on this next lecture!

Recap

Recap: Project organization & documentation

  • Use one folder per project; separate file kinds into consistent subfolders
  • Never manually edit data/results – use code
  • Use machine- and human-readable file names, sorted correctly by default
  • Prefer relative paths, starting from your project’s top-level dir
  • Maintain a README, a lab notebook, and a workflow/protocol file, in plain text (Markdown)
