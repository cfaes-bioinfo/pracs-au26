OSC Projects

OSC Projects

In this course, we exclusively use the course’s OSC Project PAS3493. For your own research, you would likely use a Project specific to a research project or grant, or your lab’s general-use Project.

Using a Project

  • Storing data in its dirs in /fs/ess and/or /fs/scratch
  • Selecting the Project when starting compute jobs, like Code Server and (later in the course) batch jobs

Managing a Project

Generally only done by PIs (more info). Project administrators can, among others:

  • Manage the compute budget and /fs/ess storage allocation
  • Add users to the Project

If a new user doesn’t have an OSC account yet, they will get an invite email — you can’t create an account unless you’ve been added to a Project.

OSC billing

OSC bills Projects (not individual users), and only for two things:

File storage

Storage in the Project dirs (/fs/ess), per TB per month.

Compute

Compute node usage per “core hour”:
using 2 cores for 2 hours = 4 core hours.

Who pays?

  • Every OSU PI gets a $1,000 credit.
  • OSU colleges pay some or all of the costs — CFAES currently pays all of it.

Prices for academic usage are generally low, but a Project using dozens of TBs and hundreds of thousands of core hours could be charged several thousand dollars per year.

Cores

Cores

In week 2, you learned that a supercomputer center has multiple supercomputers, each of which consists of many nodes. But there is one more “level”:

What is a core?

A component of a computer (node) that can (semi-)independently perform a computing task, like running a bioinformatics program.

Many programs can use multiple cores for a single run, which can speed things up considerably.

Core / Processor / CPU / Thread

These terms are not technically synonyms, but are often used interchangeably.

For working at OSC, treat them as meaning the same thing: the components of a node that can be reserved and used independently.

Quiz: Core hours

Think about it

  1. You run a program with 8 reserved cores for 3 hours. How many core hours will your OSC Project be billed for?

  2. Afterwards, you find out that the program only ever used 1 of those cores. Does that change the number of billed core hours? What does this tell you about how many cores to request?

File systems

OSC file systems

An expanded version of the table from week 2:

File system Located within Quota Backed up? Auto-purged? One for each…
Home /users/ 500 GB / 1 M files Yes No User
Project /fs/ess/ Flexible Yes No OSC Project
Scratch /fs/scratch/ 100 TB No After 60 days OSC Project
Compute $TMPDIR 1 TB No After job completes Compute job

Recommendation

For your own research, work mostly in the Project dir (/fs/ess/), which offers backed-up, permanent storage with flexible quota.

When are the other file systems useful?

Home

Drawbacks: limited space that can’t be expanded, and harder to share files with collaborators.

Useful for: files you use across projects, like some software. Also stores user-specific settings, in hidden files (.) that you should generally leave alone.

Scratch

Drawbacks: temporary and not backed up.

Useful for: large datasets, thanks to effectively unlimited space and faster read/write (“I/O”) speed. Run analyses here, then copy key files to the Project dir.

Compute

Drawbacks: extremely fleeting — files are deleted as soon as the job stops.

Useful for: very I/O-intensive jobs, with even faster I/O. But it requires extra code in your script, so I rarely use it.

Home dir clarifications & other notes

Home dir clarifications

  • The project number in your Home dir path (e.g., /users/PAS3454/jane) is merely a naming convention: your Home dir is not really tied to any OSC Project. It stays the same if you’re removed from a Project or the Project stops existing.

  • You land in your Home dir after logging in, but this is typically not where you want to be to work with data.

  • Avoid storing research project files in your Home dir.

  • Home dir will have hidden files (those starting with a .) that are generated and used automatically by software. Don’t mess with them unless you know what you’re doing!

Accessing back-ups

Home and Project dirs are backed up daily. You don’t have direct access to the backups, but you can email OSC to restore your files to the way they were on a specific date.

Files on different clusters

File systems are shared among OSC’s clusters, so you can access your files in the exact same way regardless of which cluster you’re connected to.

Compute nodes

Compute node types

“Standard” nodes

  • By far the most numerous (e.g., Pitzer has 564)
  • Even these vary in size, e.g. from 40-48 cores per node on Pitzer
  • Used by default, and will serve you well for most omics analyses

Other node types

  • Nodes with extra memory: largemem and hugemem
  • Nodes with GPUs (Graphical Processing Units) rather than CPUs

You may occasionally need these, for example for genome or transcriptome assembly (large-memory nodes) or Oxford Nanopore base-calling (GPU nodes).

Memory versus storage

When we talk about a computer’s “memory”, this refers to RAM — don’t confuse this with file storage.

Memory (RAM)

  • The data a computer has actively “loaded” or in use
  • Accessed orders of magnitude faster than data on disk
  • E.g., heavily used when you play a game or have many browser tabs open

Storage (disk)

  • The data that is saved in files on disk
  • When your computer freezes, it’s typically because memory is full and disk storage has to be used as well

Bioinformatics programs may load input data into memory for fast access, and hold intermediate results there too. With large datasets, they may need 10s or 100s of GBs of memory.

Using compute nodes

Compute jobs

You use compute nodes by requesting resources, such as a number of nodes and cores, and for how long you need them.

These requests result in “compute jobs” (or simply “jobs”). Our VS Code sessions are an example!

The job scheduler

Many users send requests all the time, so a job scheduler (Slurm at OSC) considers each request and assigns resources to jobs as they become available.

In two weeks, you’ll learn to submit scripts as “batch jobs” with Slurm.

Quiz: True or false?

True or false?

  1. If a program crashes because it runs out of memory, moving your files to a location with a larger storage quota will fix it.

  2. Requesting 8 cores instead of 1 will make any program run about 8× faster.

  3. A file you created while connected to Pitzer can also be accessed from Cardinal.
