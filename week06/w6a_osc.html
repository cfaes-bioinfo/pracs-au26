Compute nodes, compute jobs, and cores

Using compute nodes via “jobs”

Compute jobs

You use compute nodes by requesting resources, such as a number of nodes and cores, and for how long you need them.

These requests result in “compute jobs” (or simply “jobs”). Our VS Code sessions are an example!

The job scheduler

Many users send requests all the time, so a job scheduler (Slurm at OSC) considers each request and assigns resources to jobs as they become available.

In week 9, you’ll learn to submit scripts as “batch jobs” with Slurm.

What is a core?

  • A component of a computer/node that can (semi-)independently perform a computing task, like running a bioinformatics program.

  • At the same time, many programs can use multiple cores for a single run, which can speed things up considerably.

Core / Processor / CPU / Thread

  • These terms are not technically synonyms, but are often used interchangeably.

  • For working at OSC, treat them as meaning the same thing: node components that can be reserved and used independently.

Typical compute jobs use 1 node and multiple cores on that node.

A job’s resource usage is measured in core hours. For example, using 2 cores for 2 hours = 4 core hours.

Compute node types

“Standard” nodes

  • By far the most numerous (Pitzer has 564).
  • Vary in size, e.g., 40–48 cores per node on Pitzer.
  • Used by default, and will serve you well for most omics analyses.

Other node types

  • Nodes with extra memory:
    largemem and hugemem.
  • Nodes with GPUs (Graphics Processing Units) in addition to CPUs.

When are these useful?

You may occasionally need these, for example for genome or transcriptome assembly (large-memory nodes) or Oxford Nanopore base-calling (GPU nodes).

Memory versus storage

When we talk about a computer’s memory, this refers to RAM — don’t confuse this with file storage.

Memory (RAM)

  • The data a computer has actively “loaded” or in use.
  • Accessed orders of magnitude faster than data on disk.
  • E.g., heavily used when you play a game or have many browser tabs open.

Storage (disk)

  • The data that is saved in files on disk.

When your computer freezes, it’s typically because memory is full, and it starts using disk storage as “virtual memory”, which is much slower.

Bioinformatics programs may load input data into memory for fast access, and hold intermediate results there too. With large datasets, they may need 10s–100s of GBs of memory.

OSC Projects

OSC bills Project-wise

OSC bills Projects (not individual users), and only for two things:

File storage

  • File storage in the Project dirs (/fs/ess).

  • Charged per TB per month.

Compute

  • Compute node usage

  • Charged per core hour.

Who pays?

  • Every OSU PI gets a $1,000 yearly credit.
  • OSU colleges pay some or all of the costs — CFAES currently pays all of it.


Prices for academic usage are generally low, but a Project using dozens of TBs and tens of thousands of core hours could be charged over a thousand dollars per year.

Using and managing OSC Projects

In this course, we exclusively use the course’s OSC Project PAS3493. For your own research, you would likely use a Project specific to a research project or grant, or your lab’s general-use Project.

Using a Project

In practice, “using” a Project means:

  • Storing data in its /fs/ess and/or /fs/scratch dirs.
  • Selecting the Project when starting compute jobs, like Code Server and (later in the course) batch jobs.

Managing a Project

Generally only done by PIs (more info). Project administrators can, among others:

  • Manage the compute budget and /fs/ess storage allocation.
  • Add users to the Project.

There is a fourth storage area, compute, that is on compute nodes and is deleted when a job ends.
In practice, this is rarely needed in bioinformatics, and we won’t use it in this course.

When are different storage areas useful?

Project

  • Drawbacks: storage is billed (per TB per month), and read/write (“I/O”) is slower than on Scratch.

  • Useful for: everything you want to keep long-term: raw data, scripts, documentation, and key results.

Scratch

  • Drawbacks: temporary and not backed up.

  • Useful for: analysis of large datasets, thanks to effectively unlimited space and faster I/O.

    For those: run analyses here, then copy key files to the Project dir.

Home

  • Drawbacks: limited space that can’t be expanded, and harder to share files with collaborators.

  • Useful for: files you use across projects, like some software.

Storage areas: misc. notes

  • Hidden files in the Home dir
    Your Home dir will have hidden files (those starting with a .) that are generated and used automatically by software. Don’t mess with them unless you know what you’re doing!
  • Accessing backups
    Home and Project dirs are backed up daily. You don’t have direct access to the backups, but you can email OSC to restore your files to the way they were on a specific date.
  • Accessing files across clusters
    OSC’s clusters share the entire file system, so you can access your files in the exact same way regardless of which cluster you’re connected to.

Side note: Why have multiple clusters?

OSC buys a new cluster every few years and retires the oldest one, so the clusters differ in age and hardware:

  • Pitzer (2018, expanded in 2020)
  • Ascend (2022, with many GPU nodes)
  • Cardinal (2024, the newest)

Rolling out clusters this way is beneficial, for example, because it keeps some hardware always up to date while avoiding downtime for the entire center.

Direct Unix shell access

The Clusters dropdown menu gives direct access to a Unix shell on any of the three clusters.

  • While we use Code Server in the course to access a shell, the Clusters dropdown can occasionally be useful as a quicker access point.
  • Be aware that you will be on a login node, so you have less leeway in terms of memory and CPU usage than on a compute node for testing purposes.

Other options

Installing software yourself?

Installing software like you would on your own computer is often not possible at OSC:

  • You don’t have administrator privileges.
  • You will often run into issues with dependencies (other software that a program depends on).

Conda and containers

  • Conda: Allows you to install software into “environments” you can load.

  • Containers: Self-contained software packages that can be distributed.

  • Both:

    • Bypass the dependency and administrator privilege issues.
    • Make it easy to switch between versions of the same software, or to use mutually incompatible software.
    • Are highly reproducible.

Conda versus containers

The two approaches are quite different, both conceptually and in practice:

Aspect Conda Container
Setup Install once, then load Download file, run directly
Combining tools Easier Harder
Reliability Installs can be slow or fail Quick and reliable to obtain
Files Many small files (may hit OSC quota) Single file
Portability Less portable Highly portable & reproducible


What is available?

Generally, the same set of programs is available through Conda and as containers, all of which is free, open-source software. If a program isn’t available, it tends to be a sign it’s outdated, poorly maintained, or poorly documented, and better avoided anyway (exceptions exist).

Other ways to get software at OSC

  • Email OSC Help
    They may be able to help with your installation, or, for commonly used software, may be willing to do a system-wide installation (i.e., make it available as a module).
